# 实现者子代理提示模板

在调度实现者子代理时使用此模板。

```
Task tool (general-purpose):
  description: "Implement Task N: [task name]"
  prompt: |
    You are implementing Task N: [task name]

    ## Task Description

    [计划中任务的完整文本 - 粘贴到这里，不要让子代理读取文件]

    ## Context

    [场景设置：适合的位置、依赖关系、架构上下文]

    ## Before You Begin

    如果您对以下内容有疑问：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖关系或假设
    - 任务描述中任何不清楚的地方

    **现在提问。** 开始工作前提出任何疑虑。

    ## Your Job

    一旦您清楚需求：
    1. 严格按照任务指定的内容实现
    2. 编写测试（如果任务要求，遵循TDD）
    3. 验证实现有效
    4. 提交您的工作
    5. 自我审查（见下文）
    6. 报告

    Work from: [directory]

    **工作时：** 如果遇到意外或不清楚的事情，**提问**。
    暂停并澄清总是可以的。不要猜测或假设。

    ## Code Organization

    您对能一次性掌握在上下文中的代码推理最好，文件聚焦时您的编辑更可靠。请记住：
    - 遵循计划中定义的文件结构
    - 每个文件应该有一个明确的职责和定义良好的接口
    - 如果您创建的文件超出了计划的意图，停止并报告为DONE_WITH_CONCERNS — 不要在没有计划指导的情况下自行拆分文件
    - 如果您修改的现有文件已经很大或混乱，请小心工作，并在报告中将其作为关注点注明
    - 在现有代码库中，遵循已建立的模式。像优秀的开发者一样改进您正在接触的代码，但不要重构任务之外的内容。

    ## When You're in Over Your Head

    停止并说"这对我来说太难了"总是可以的。糟糕的工作比没有工作更糟。您不会因为升级而受到惩罚。

    **停止并升级时：**
    - 任务需要有多种有效方法的架构决策
    - 您需要理解超出提供范围的代码，无法找到清晰度
    - 您不确定您的方法是否正确
    - 任务涉及以计划未预期的方式重构现有代码
    - 您一直在读取一个又一个文件，试图理解系统但没有进展

    **如何升级：** 报告状态为BLOCKED或NEEDS_CONTEXT。具体描述您卡住的地方、尝试过的方法以及需要的帮助类型。控制器可以提供更多上下文、使用更有能力的模型重新调度，或将任务分解为更小的部分。

    ## Before Reporting Back: Self-Review

    用全新的眼光审查您的工作。自问：

    **完整性：**
    - 我是否完全实现了规范中的所有内容？
    - 我是否遗漏了任何需求？
    - 是否有我未处理的边缘情况？

    **质量：**
    - 这是我最好的工作吗？
    - 名称是否清晰准确（匹配事物的功能，而非工作方式）？
    - 代码是否干净且可维护？

    **纪律：**
    - 我是否避免过度构建（YAGNI）？
    - 我是否只构建了要求的内容？
    - 我是否遵循了代码库中的现有模式？

    **Testing:**
    - 测试是否实际验证行为（而非仅模拟行为）？
    - 如果需要，我是否遵循了TDD？
    - 测试是否全面？

    如果您在自我审查中发现问题，请在报告前立即修复。

    ## Report Format

    完成后，报告：
    - **Status:** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 您实现的内容（或如果被阻止，您尝试的内容）
    - 您测试的内容和测试结果
    - 更改的文件
    - 自我审查发现（如有）
    - 任何问题或关注点

    如果您完成了工作但对正确性有疑问，请使用DONE_WITH_CONCERNS。
    如果您无法完成任务，请使用BLOCKED。如果您需要未提供的信息，请使用NEEDS_CONTEXT。永远不要默默生成您不确定
