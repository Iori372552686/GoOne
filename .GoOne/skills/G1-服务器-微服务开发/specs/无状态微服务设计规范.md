# 无状态微服务设计规范

> 版本：v1.1
> 适用范围：所有基于 GoOne 框架（`lib/service/`）的无状态微服务
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]]

---

## 一、无状态服务的定义

无状态微服务是指**每个请求独立处理，不依赖前一个请求的状态，也不维护进程内用户数据缓存**的服务。在 GoOne 框架中，这类服务通过 `SvrRouterRule_Random`（或 `Master`）将请求分发到任意可用实例。

### 1.1 框架层特征

| 特征 | 取值 |
|------|------|
| 路由规则 | `SvrRouterRule_Random`（随机）或 `Master`（主备） |
| UID 依赖 | 可选（仅作为业务参数，不参与路由决策） |
| 组件模型 | `runtime.Component`（Start/Stop） |
| 装配方式 | `bussvc.MustNew("<svc>", router.ReadyCheck, ...)` + `MustRegister` |
| 典型服务 | web_svr（HTTP/gRPC 对外）、chat |

### 1.2 消息流路径

```
Client → connsvr → router(按 cmd 的 ServerType + ServerRouteRules=Random) → 任意实例
                                                                       ↓
                                                                 globals.TransMgr
                                                                 (sharded，但无状态请求无 key 粘性)
                                                                       ↓
                                                                 ssrpc Dispatcher
                                                                       ↓
                                                                 middleware 链 → handler
                                                                       ↓
                                                                 lib/db/redis 或 ssrpc 调用
```

> web_svr 例外：直接对外 HTTP(Gin)/gRPC，不经 connsvr/bus。

## 二、架构约束（强制标准）

### 2.1 状态约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **U-01** | 禁止在进程内存中缓存用户数据 | 同一用户请求可能路由到不同实例，缓存不一致 |
| **U-02** | 禁止使用 `sync.Map` / `map` 存储用户级状态 | 实例重启数据丢失，不同实例数据不同步 |
| **U-03** | 禁止依赖请求间的执行顺序 | 随机路由可能导致请求乱序到达 |
| **U-04** | 禁止在请求处理中创建长生命周期对象 | 内存泄漏，GC 压力 |

### 2.2 路由约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **U-05** | 必须使用 `SvrRouterRule_Random`（或 `Master`） | 注册到 `module/misc/constant.go` 的 `ServerRouteRules` |
| **U-06** | 不能用 `Hash_UID`/`Hash_RouterID`（那是有状态路由） | 会导致粘性，违背无状态语义 |
| **U-07** | ssrpc handler 经 `Register<Svc>ToRegistry` 注册 | CI 门禁禁止旧 API |

### 2.3 数据访问约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **U-08** | 所有数据读写通过 `lib/db/redis` 或 ssrpc 跨服务调用 | 绕过接口无法利用连接池 |
| **U-09** | 禁止在无状态服务中使用跨请求事务 | 不同请求可能路由到不同实例，无法保证原子性 |
| **U-10** | 对同一用户的并发写入必须通过 Redis 原子操作保护 | 竞态条件导致数据错乱 |

### 2.4 并发约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **U-11** | 必须假设同一 `uid` 的请求可以并发到达不同实例 | 设计上不能依赖单实例串行化 |
| **U-12** | 幂等操作用 Redis `SetBytesEx` + NX 语义 | 避免重复创建 |
| **U-13** | 计数操作用 Redis 原子递增（`IncrKey`） | 避免读写竞争 |

## 三、容量规划标准

### 3.1 单实例容量公式

```
QPS_max = min(
    DB/Redis连接池大小 / 平均操作耗时,
    CPU核心数 / 平均CPU耗时,
    网络带宽 / 平均响应大小
)

所需实例数 = ceil(预估峰值QPS / QPS_max × 1.5)
```

### 3.2 扩展策略

- **水平扩展**：直接增加实例数，router 自动随机分发
- **瓶颈转移**：高 QPS 场景将热点数据缓存到 Redis

### 3.3 DAU 与 QPS 换算

```
峰值 QPS = DAU × 活跃时段操作频率 × 集中系数

示例：
  DAU = 10万，平均每人每小时操作 10 次，集中系数 = 3
  峰值 QPS ≈ 100,000 × 10 / 3600 × 3 ≈ 833 QPS
```

## 四、数据一致性策略

### 4.1 一致性等级选择

| 等级 | 含义 | 适用场景 | 实现方式 |
|------|------|---------|---------|
| **强一致** | 写入后立即读到最新值 | 货币操作、关键状态变更 | Redis 原子操作 / MySQL 主库写 |
| **最终一致** | 写入后最终能读到最新值 | 非关键的展示数据 | Redis 缓存 + TTL |
| **弱一致** | 不保证立即读到最新值 | 排行榜、统计 | Redis 异步更新 |

### 4.2 原子操作选择

| 场景 | 推荐操作 | 说明 |
|------|---------|------|
| 插入（防重复） | Redis `SetBytesEx` + NX 语义 | key 已存在时拒绝 |
| 计数 | Redis `IncrKey` | 利用 Redis 原子性 |
| 扣减（防超扣） | Redis `IncrKey` + 检查返回值 < 0 则回滚 | 利用 Redis 原子性 |

### 4.3 缓存策略

```
读取流程：
  1. 查 Redis 缓存
  2. 命中 → 返回
  3. 未命中 → 查 MySQL（经 mysqlsvr ssrpc）或远端
  4. 写入 Redis（设置 TTL）
  5. 返回

写入流程：
  1. 写权威存储
  2. 删除 Redis 缓存（而非更新）
  3. 下次读取时重建缓存

注意：无状态服务不能使用进程内缓存！
```

## 五、错误处理标准

### 5.1 错误返回规范

| 错误类型 | 返回方式 | 示例 |
|---------|---------|------|
| 参数校验失败 | ssrpc 返回 `gerr.New(...)` | 必填字段缺失 |
| 业务逻辑错误 | ssrpc 返回 `gerr.New(...)` | 余额不足 |
| 系统错误 | 记录日志 + 返回通用错误码 | DB 连接超时 |
| Panic | `safego.Go`/中间件 recover + 日志 | 空指针 |

> 统一用 `lib/api/gerr`（或 ssrpc 的 `ssrpc.E`/`Wrap`）；禁裸 `errors.New` 穿越 RPC；禁 `rsp.Ret.Code = ERR_X` 后 `return rsp, nil`。

### 5.2 超时控制

| 操作 | 建议超时 | 说明 |
|------|---------|------|
| Redis 操作 | 1s | 内存操作应极快 |
| MySQL（经 ssrpc） | proto `timeout_ms`（service 级默认） | - |
| ssrpc 调用 | `timeout_ms` option | - |

### 5.3 重试策略

| 场景 | 策略 | 说明 |
|------|------|------|
| 连接超时 | 不重试 | 避免雪崩 |
| 业务幂等操作 | 最多 1 次重试 | 确保消息送达 |
| 业务非幂等操作 | 不重试 | 避免重复副作用 |

## 六、服务间通信规范

### 6.1 通信方式选择

| 方式 | 使用场景 | API |
|------|---------|-----|
| **ssrpc 调用（S2S）** | 调用其他服务 | `<svc>v1.New<Svc>Client().Method(trans, &req)` |
| **下行 Push（S2C）** | 推消息给客户端 | 经 connsvr 的 `ConnService` 或下行 cmd（`SC_*`） |
| **事件** | 服务内组件广播状态变更 | EventBus.Publish |

### 6.2 ssrpc 调用约束

| 编号 | 约束 | 说明 |
|------|------|------|
| **U-14** | 不依赖调用结果（fire-and-forget 优先） | 避免级联故障 |
| **U-15** | ssrpc 消息带 UID | 配合 `uid_lock` option 串行化 |
| **U-16** | 不跨服务做分布式事务 | 使用补偿机制 |

## 七、监控与可观测性

### 7.1 必须监控的指标

| 指标 | 含义 | 告警阈值 |
|------|------|---------|
| QPS | 每秒请求数 | 超过容量规划的 80% |
| 成功率 | 成功响应 / 总请求 | < 99.9% |
| P99 延迟 | 99% 请求的响应时间 | > 500ms |
| 错误率 | 错误响应 / 总请求 | > 0.1% |

> 可观测性基建见 `docs/observability/README.md`（OpenTelemetry + OTLP + Prometheus）。

### 7.2 必须记录的日志

| 日志级别 | 内容 | 示例 |
|---------|------|------|
| Info | 关键操作 | 用户登录成功 |
| Warn | 异常但可恢复 | 参数校验失败 |
| Error | 不可恢复错误 | DB 连接超时 |

> 统一用 `lib/api/logger`；热路径 Debug 日志加 `logger.DebugEnabled()` 前置。

## 八、设计检查清单

### 启动前检查

- [ ] 服务类型确认：不依赖请求间状态 □
- [ ] 路由规则：`SvrRouterRule_Random`（或 `Master`） □
- [ ] 数据访问：通过 `lib/db/redis` 或 ssrpc □
- [ ] 进程内缓存：无用户级数据缓存 □
- [ ] 并发安全：通过 Redis 原子操作保证 □
- [ ] 容量规划：已按 DAU 目标计算实例数 □
- [ ] 错误处理：所有异常都有兜底逻辑 □
- [ ] 禁止模式：不存在 U-01 到 U-16 违规项 □

## 十、常见反模式与纠正

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| "伪无状态" | 使用 sync.Map 缓存玩家数据 | 改为 Redis 缓存或升级为有状态服务 |
| "跨请求事务" | 在 handler 中创建事务对象等到下次请求使用 | 使用 Redis 原子操作一次性完成 |
| "阻塞式 ssrpc" | 同步等待另一个服务返回结果 | 改用事件驱动或异步回调 |
| "DB 穿透" | 大量无缓存请求直接压存储 | 热点数据加 Redis 缓存层 |
