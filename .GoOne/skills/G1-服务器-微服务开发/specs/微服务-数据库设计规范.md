# 微服务-数据库设计规范

> 版本：v2.1
> 适用范围：所有基于 GoOne 框架（`lib/service/`）的微服务
> 核心架构：服务实例级路由（`SvrRouterRule_*`）+ xorm 主从（MySQL）+ Redis 多实例
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]] | `.GoOne/spec/03-玩家服务数据库协议规范文档.md` | `.GoOne/spec/04-游戏微服务数据库协议规范文档.md`

---

## 一、核心架构与约定

### 1.1 架构总览

GoOne **不使用 MongoDB，也没有 dbrouter / 分库分表 / 应用层分片**。数据存储分两层，分片只在**服务实例层**（按 `SvrRouterRule_*` 路由到服务实例），而非数据库层：

```
                    服务实例路由（lib/service/svrinstmgr）
                ┌──────────────┬───────────────┬──────────────┐
                │  Hash_UID    │ Hash_RouterID │   Random     │
                │ (mainsvr/    │ (mysqlsvr/    │ (web_svr/    │
                │  infosvr)    │  roomcenter)  │  chat)       │
                └──────┬───────┴───────┬───────┴──────┬───────┘
                       │               │              │
                 ┌─────▼─────┐  ┌──────▼──────┐  ┌────▼──────┐
                 │  mainsvr  │  │  mysqlsvr   │  │  web_svr  │
                 │  实例群   │  │  实例群     │  │  实例群   │
                 └─────┬─────┘  └──────┬──────┘  └───────────┘
                       │               │
                 ┌─────▼─────┐  ┌──────▼──────┐
                 │  Redis    │  │   MySQL     │
                 │  多实例   │  │  xorm 主从  │
                 │ (玩家hash │  │ (role_info +│
                 │  落盘)    │  │  Texas 三表)│
                 └───────────┘  └─────────────┘
```

### 1.2 强制约定

| 编号 | 约定 | 说明 |
|------|------|------|
| **DB-01** | ❌ **GoOne 无 dbrouter / 分库分表** | 不要引入 `StrategyHash`/`StrategyMod`/`StrategyRange` 等概念；分片在服务实例层 |
| **DB-02** | ✅ **关系型用 MySQL**（`lib/db/xorm`，主从 `EngineGroup`） | mysqlsvr 持久化结构化数据 |
| **DB-03** | ✅ **KV / 缓存用 Redis**（`lib/db/redis`，多实例按 `instID`） | mainsvr 玩家数据 hash 落盘、infosvr 缓存、roomcentersvr 快照 |
| **DB-04** | ✅ **Redis 生产环境强制 Sentinel / Cluster** | 禁止单机 |
| **DB-05** | ⚠️ **Redis 可作权威存储**（mainsvr 玩家主数据落 Redis hash） | 与 Seed 不同，GoOne 玩家主数据就在 Redis，MySQL 仅存少量关键字段 |

### 1.3 与 Seed 架构的关键差异

| 维度 | Seed | GoOne |
|------|------|-------|
| 主存储 | MongoDB（整文档 DbUserData） | Redis hash（mainsvr 直连） |
| 关键字段 | MongoDB | MySQL `role_info`（经 mysqlsvr，当前仅 uid+name） |
| 分片 | dbrouter 应用层（Hash/Mod/Range） | **无**；服务实例级（`SvrRouterRule_*`） |
| 战斗/房间数据 | MongoDB | MySQL（mysqlsvr 的 Texas 三表） |

## 二、服务实例路由（`lib/service/svrinstmgr`）

### 2.1 路由规则

实现在 `lib/service/svrinstmgr/svr_inst_mgr.go`：

| 规则 | 实现 | 适用服务 |
|------|------|---------|
| `Hash_UID` | `svrs[uid % len]` | mainsvr、infosvr、mailsvr、friendsvr |
| `Hash_RouterID` | `svrs[routerID % len]` | mysqlsvr、roomcentersvr、guildsvr、Texas/Rummy |
| `Hash_ZoneID` | `svrs[zoneID % len]` | ranksvr |
| `Random` | `rand.Int31n` | web_svr、chatsvr、gmsvr |
| `Master` | `svrs[0]`（主备） | - |
| `ConsistentHash_UID/ZoneID/RouterID` | 一致性哈希环 | 扩缩容少迁移场景 |
| `IoCache_RouterID` | 一致性哈希 | - |

### 2.2 路由配置

路由规则在 `module/misc/constant.go` 的 `ServerRouteRules`（`map[uint32]uint32`）中静态注册：

```go
var ServerRouteRules = map[uint32]uint32{
    ServerType_MainSvr:        SvrRouterRule_Hash_UID,
    ServerType_MysqlSvr:       SvrRouterRule_Hash_RouterID,
    ServerType_InfoSvr:        SvrRouterRule_Hash_UID,
    ServerType_RoomCenterSvr:  SvrRouterRule_Hash_RouterID,
    ServerType_WebSvr:         SvrRouterRule_Random,
    // ...
}
```

> 业务代码**不需要手动路由**。跨服务调用经 ssrpc client，router 按 `ServerRouteRules` 自动选定目标实例。

## 三、Redis 访问（`lib/db/redis`）

### 3.1 多实例配置

Redis 实例经 `base_cfg.dependencies.db_instances`（`[]redis.Config`）配置，`InitAndRun(dbIns)` 启动：

```yaml
base_cfg:
  dependencies:
    db_instances:
      - { inst_id: "player", ip: "...", port: 6379, password: "...", db_index: 0 }
      - { inst_id: "room",   ip: "...", port: 6380, password: "...", db_index: 0 }
```

### 3.2 访问 API

```go
cli := rds.RedisMgr.GetClient(instID)
cli.SetBytes(key, val) / SetBytesEx(key, val, ttl)
v, _ := cli.GetBytes(key)
cli.DelKey(key)
cli.IncrKey(key)
cli.ZsetSet(key, member, score) / ZsetRange(key, start, stop)
```

### 3.3 各服务 Redis 用途

| 服务 | instID 域 | 用途 |
|------|-----------|------|
| mainsvr | player | 玩家数据 hash 落盘（`persist_hash.go`）、IDGen |
| infosvr | cache | BriefInfo / IconDesc 缓存 |
| roomcentersvr | room | 房间列表快照（启动恢复 + 定时持久化） |
| web_svr / connsvr | - | sign / rest 配置 |

## 四、MySQL 访问（`lib/db/xorm`）

### 4.1 ORM 配置

实例经 `base_cfg.dependencies.orm_instances`（`[]orm.Config`）配置：

```yaml
base_cfg:
  dependencies:
    orm_instances:
      - { index_name: "main", master: {...}, slaves: [...] }
```

`OrmMgr.InitAndRun` 启动，`AddInstance(conf, tables...)` 支持主 + 多从，`SyncTables` 自动建表。

### 4.2 mysqlsvr 表清单

`src/mysqlsvr/manager/table_mgr.go` 同步的 ORM 表：

```go
var tables = []interface{}{
    new(g1_protocol.MysqlTexasRoomInfo),
    new(g1_protocol.MysqlTexasPlayerInfo),
    new(g1_protocol.MysqlTexasGameInfo),
}
```

另有 `role_info` 表（uid + name），用裸 SQL 访问。

### 4.3 异步写库

mysqlsvr 用 `async.NewAsyncPool(15)` 异步落库，按 `id % 15` 分发，避免阻塞事务。

## 五、存储选型标准

### 5.1 选型决策

| 场景 | 选择 | 原因 |
|------|------|------|
| 玩家主数据（频繁读写、需内存缓存） | Redis hash（mainsvr 直连） | 低延迟，内存命中 |
| 玩家关键字段（name 等） | MySQL `role_info`（经 mysqlsvr ssrpc） | 关系型，可查询 |
| 房间/对局明细 | MySQL（mysqlsvr Texas 三表） | 结构化记录 |
| 缓存/查询（BriefInfo） | Redis（infosvr） | 低延迟 |
| 排行榜/排序 | Redis Sorted Set | 高效排序和范围查询 |
| 实时计数 | Redis 原子操作 | 原子递增/递减 |
| 对外 HTTP/gRPC 接口 | web_svr（不持有自有数据） | 经 ssrpc 读其他服务 |

### 5.2 Redis 适用场景约束

| 编号 | 约束 | 说明 |
|------|------|------|
| **DB-06** | 排行榜/排序类数据使用 Redis Sorted Set | 高效排序 |
| **DB-07** | 实时计数器使用 Redis 原子操作 | 在线人数、签到次数等 |
| **DB-08** | 热点数据缓存使用 Redis，必须设置 TTL（除非是权威数据） | 避免缓存无限增长 |

## 六、数据结构定义标准

### 6.1 Redis Key 设计

| 编号 | 约束 | 说明 |
|------|------|------|
| **DB-09** | Key 命名：`{模块}:{ID}:{子项}` | 如 `player:data:10001`、`room:list:zone1` |
| **DB-10** | 所有 Key 必须明确 TTL | 不设 TTL 的必须注释"永久"或"权威数据" |
| **DB-11** | Redis 数据类型选择必须有理由 | 为什么用 Hash 而非 String？（mainsvr 玩家数据用 hash 便于按模块增量） |

### 6.2 MySQL 表设计

| 编号 | 约束 | 说明 |
|------|------|------|
| **DB-12** | 每张表必须明确定义用途 | 一句话说清楚存什么 |
| **DB-13** | 主键必须是业务主键 | uid、room_id 等 |
| **DB-14** | ORM 表 struct 注册到 `table_mgr.go` 的 `tables` 列表 | mysqlsvr 启动时 `SyncTables` 自动建表 |
| **DB-15** | 字段注释写"业务含义"而非"技术描述" | "玩家当前等级"而非"int32 字段" |

### 6.3 数据生命周期

| 阶段 | 必须回答 |
|------|---------|
| 创建 | 创建时机？谁创建？默认值？ |
| 更新 | 频率？方式（全量/增量）？并发处理（serial key）？ |
| 查询 | 频率？条件？是否需要缓存？ |
| 清理 | 保留多久？TTL 还是归档？ |

## 七、数据一致性

| 编号 | 约束 | 说明 |
|------|------|------|
| **DB-16** | 必须明确 Redis 和 MySQL 的角色 | mainsvr：Redis hash 是玩家主数据；mysqlsvr：MySQL 存少量关键字段 |
| **DB-17** | 关键数据（货币、道具）先落库再更新内存 | 防止宕机丢失 |
| **DB-18** | 普通数据可先更新内存标记脏数据，定时批量回写 | 性能优先 |
| **DB-19** | 货币/道具操作必须强一致 | 用户看到的余额必须实时准确 |
| **DB-20** | 同一 UID 的核心数据聚合在同一服务（mainsvr RoleMgr） | 避免跨服务一致性问题 |

## 八、玩家服务存储方案（mainsvr）

mainsvr 采用 **Redis hash 按模块增量** 模式（见 `.GoOne/spec/03-玩家服务数据库协议规范文档.md`）：

| 方法 | 说明 |
|------|------|
| `Role.SaveToDB(trans)` | 按模块增量写 Redis hash（`saveRoleHash`） |
| `Role.SaveToMysql(trans)` | 经 ssrpc 调 mysqlsvr 落 `role_info`（当前仅 name） |
| `Role.SaveToDBSync()` | 同步写 Redis，用于优雅停机全量落盘 |

定时落盘：`roleTick`（`scheduler.New("role_tick", time.Minute)`）每分钟 `RoleMgr.Tick()`。
停机落盘：`roleFlushComponent`（Drainer）全量 `SaveToDBSync`。

## 九、通用 KV 抽象（`common/game_proto/storage/`）

面向独立 dbsvr 的统一 KV 接口（`storage/dbsvr.proto`）：

| 方法 | 说明 |
|------|------|
| `DBUidGet` / `DBUidSet` | 按 UID 的 KV 读写 |
| `DBCommGet` / `DBCommSet` / `DBCommDel` / `DBCommIncr` | 通用 KV |
| `DBCommZsetSet` / `DBCommZsetGet` / `DBCommFindRank` / `DBCommZRevRange` | 有序集合（排行榜） |
| `DBCommExpire` / `DBCommSetExNx` | 过期 / NX |

> 这套抽象面向未来的统一 dbsvr 服务。当前 mysqlsvr 未使用它（走 ORM + 裸 SQL）。

## 十、备份与恢复

| 编号 | 约束 | 说明 |
|------|------|------|
| **DB-21** | MySQL 主从自带高可用，Master 故障切到 Slave | xorm `EngineGroup` 自动读写分离 |
| **DB-22** | 定期执行 MySQL 逻辑备份到异地存储 | 防止误操作或逻辑损坏 |
| **DB-23** | Redis 必须开启 RDB + AOF 持久化 | 防止宕机丢数据 |
| **DB-24** | mainsvr 玩家主数据在 Redis hash，停机经 Drainer 全量落盘 | `roleFlushComponent` 保证数据不丢 |
