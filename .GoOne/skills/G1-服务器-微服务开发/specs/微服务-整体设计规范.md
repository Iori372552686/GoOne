# 微服务-整体设计规范

> 版本：v1.1
> 适用范围：所有基于 GoOne 框架（`lib/service/`）的微服务
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]]

---

## 一、规范定位

本规范定义了每个微服务在输出整体设计方案时必须达到的设计深度和质量标准。整体设计方案是服务的顶层设计文档，描述服务的定位、架构决策、容量规划和全局约束。

### 1.1 规范要求

整体设计方案必须覆盖以下 8 个维度：

| 维度 | 核心问题 | 不合格标准 |
|------|---------|-----------|
| **服务定位** | 服务做什么、不做什么？边界在哪？ | 边界模糊，职责与已有服务重叠 |
| **架构模式** | 为什么选这种架构模式？有数据支撑吗？ | 选型无依据，未走决策树 |
| **目录结构** | 代码目录如何组织？遵循哪种范式？ | 结构随意，与项目约定不一致 |
| **服务拓扑** | 与其他服务的依赖关系是什么？ | 依赖关系未穷举，遗漏 ssrpc 接口 |
| **容量规划** | 以什么 DAU 为目标？实例数如何算出？ | 容量的计算公式有错误/遗漏 |
| **约束检查** | 所有强制约束是否通过检查？ | 有"必须"级别的约束未满足 |
| **风险评估** | 识别了哪些风险？有应对吗？ | 风险清单为空或敷衍 |
| **版本管理** | 方案的版本号是多少？变更记录在哪？ | 无版本号，无变更日志 |

## 二、服务定位标准

### 2.1 定位陈述要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-01** | 必须用 3-5 句话描述服务的核心职责 | 足够简洁才能暴露边界模糊的问题 |
| **OA-02** | 必须明确列出"不做什么" | 防止职责爬行，避免与已有服务冲突 |
| **OA-03** | 必须描述服务的业务入口和出口 | 谁调用这个服务（C2S via connsvr / S2S via ssrpc）？输出给谁？ |
| **OA-04** | 必须与已有服务的定位做差异化对比 | 如果是新建服务，说明为什么不能合入已有服务（connsvr/mainsvr/infosvr/mysqlsvr/roomcentersvr/web_svr） |

### 2.2 边界检查清单

- [ ] 这个服务的职责是否唯一且明确？
- [ ] 这个服务与已有的服务之间是否有职责重叠？
- [ ] 这个服务对外暴露的接口数量是否合理？
- [ ] 这个服务的数据是否与已有服务的数据有循环依赖？

## 三、架构模式决策标准

### 3.1 强制决策路径

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-05** | 必须走完整的无状态/有状态决策树 | 不可跳过决策步骤直接选型 |
| **OA-06** | 必须在文档中回溯决策路径 | 每一步的选择都要写出"为什么"以及"为什么不选另一种" |
| **OA-07** | 必须引用运营数据支撑容量决策 | DAU、PCU、QPS 必须有来源 |
| **OA-08** | 独立服务 vs 合并到已有服务的决策必须有量化依据 | 不能仅凭"感觉"做决策 |

### 3.2 架构选型权衡表

必须逐项填写以下权衡并给出理由：

| 权衡维度 | 选择的倾向 | 代价 | 可接受的代价上限 |
|---------|-----------|------|----------------|
| 一致性 vs 性能 | {强一致 / 最终一致 / 弱一致} | {代价描述} | {什么情况下不可接受} |
| 内存 vs DB 压力 | {内存缓存 / DB 直读} | {代价描述} | {什么情况下不可接受} |
| 开发复杂度 vs 运维复杂度 | {倾向} | {代价描述} | {什么情况下不可接受} |

## 四、目录结构标准

### 4.1 目录范式

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-09** | 目录结构必须符合 GoOne 双层范式：`cmd/<svc>/main.go`（入口）+ `src/<svc>svr/`（实现） | 见 [06-游戏服务开发规范.md](../../spec/06-游戏服务开发规范.md) |
| **OA-10** | 目录路径必须使用项目约定的命名 | `src/<svc>svr`（连写，如 `roomcentersvr`）；存量 `web_svr` 保留但新服务禁用下划线 |
| **OA-11** | 必须画出完整的目录树 | 包含所有子目录和关键文件（`app.go`、`globals/`、`service/`） |
| **OA-12** | 必须标注每个目录/文件的职责 | 一句描述即可 |

## 五、服务拓扑标准

### 5.1 依赖关系完备性

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-13** | 必须穷举所有外部依赖 | 调用了哪些服务的哪些 ssrpc 接口 |
| **OA-14** | 必须穷举所有被依赖方 | 哪些服务会调用本服务的哪些接口 |
| **OA-15** | 必须标注每种依赖的通信方式 | ssrpc 调用 / 经 connsvr 下行 Push / 广播 |
| **OA-16** | 必须画出依赖拓扑图 | ASCII 或文本描述的依赖关系树 |

### 5.2 路由表要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-17** | 必须列出 `ServerType`、路由规则（`SvrRouterRule_*`）、cmd 号段 | 区分 client cmd（MsgType 0/3）/ inner cmd（MsgType 1）/ gm cmd（MsgType 0xa） |
| **OA-18** | `ServerType` 与 cmd 号段分配必须遵循号段表 | 不可与已有服务冲突（见 `module/misc/constant.go`） |
| **OA-19** | 必须说明每条路由的业务用途 | 一句话描述其处理的功能 |

## 六、容量规划标准

### 6.1 容量计算强制要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-20** | 必须基于 DAU 目标计算，不可凭空估算 | DAU 来源必须是运营目标或需求分析报告 |
| **OA-21** | 无状态服务：单实例 QPS 上限 = DB连接池 / 平均DB耗时 | 使用项目实际的连接池配置 |
| **OA-22** | 有状态服务：单节点最大在线 = 节点内存 × 0.7 / 单玩家内存 | 必须给出单玩家内存的估算依据 |
| **OA-23** | 必须乘以冗余系数 | 无状态 1.5x，有状态 1.3x |
| **OA-24** | 必须列出扩容触发条件和策略 | 什么指标到什么阈值时触发扩容 |
| **OA-25** | 必须区分常规扩容和紧急扩容的场景和流程 | 两者的操作步骤和风险不同 |

### 6.2 容量验证清单

- [ ] DAU 来源明确（运营目标 / 需求分析报告）
- [ ] 峰值 QPS / 峰值在线换算过程清晰
- [ ] 单实例容量公式正确，分母分子有依据
- [ ] 冗余系数已应用
- [ ] 扩容触发条件可量化
- [ ] 缩容策略已定义

## 七、约束检查标准

### 7.1 必须通过的强制检查

设计方案中必须逐项核验以下清单，全部通过后才能提交评审：

**基础约束**：
- [ ] 服务类型与架构模式匹配
- [ ] `ServerType` 与 cmd 号段未与已有服务冲突
- [ ] 路由规则正确（无状态=`Random`，有状态=`Hash_UID`/`Hash_RouterID`）
- [ ] 数据访问通过 `lib/db/redis` 或 ssrpc 跨服务调用
- [ ] 无违反 F-01 到 F-08 的禁止模式（见 SKILL.md）

**架构约束**：
- [ ] 如果是无状态：SL-01 到 SL-06 全部通过
- [ ] 如果是有状态：SF-01 到 SF-11 全部通过
- [ ] 如果是新建服务：`ServerType` 申请流程已完成
- [ ] 如果是优化已有服务：存量文档已读取，变更点已标注

**容量约束**：
- [ ] 实例数/节点数计算正确
- [ ] 冗余系数已应用
- [ ] 扩容触发条件已定义

## 八、风险识别标准

### 8.1 必须覆盖的风险类别

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-26** | 必须覆盖性能风险 | 单节点容量超限、DB 连接池耗尽、热点数据 |
| **OA-27** | 必须覆盖可用性风险 | 节点宕机、网络分区、依赖服务不可达 |
| **OA-28** | 必须覆盖数据风险 | 数据丢失、serial key 队列积压、跨存储不一致 |
| **OA-29** | 每个风险必须有可量化的触发条件和监控指标 | "什么时候算触发了这个风险"必须能用数字回答 |

### 8.2 风险表格要求

每个风险条目必须包含：
- 风险描述（一句话）
- 触发条件（可量化的阈值）
- 影响范围（影响哪些用户、哪些功能）
- 应对策略（预防 + 应急）
- 监控指标（需要监控什么、告警阈值）

## 九、生命周期管理标准

### 9.1 服务启动流程

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-30** | 必须描述 `bussvc.MustNew` 装配 → `MustRegister` → `Run` 的完整流程 | 每一步做什么、依赖什么（见 [06-游戏服务开发规范.md](../../spec/06-游戏服务开发规范.md)） |
| **OA-31** | 有状态服务必须描述用户登录→数据加载的流程 | 经 connsvr → mainsvr RoleMgr 加载 → 上线的时序 |

### 9.2 优雅下线流程

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-32** | 有状态服务必须装配 Drainer 全量落盘 Component | 否则节点关闭时用户数据丢失 |
| **OA-33** | 优雅下线状态机：`Ready → Draining(readyz=503) → Stopping → Stopped` | Quiesce 先于 Drain 先于 Stop |
| **OA-34** | 必须估算下线耗时并评估是否可接受 | 1000 在线玩家 × 单玩家 Save 时间 = 总耗时 |

## 十一、版本兼容性标准

### 11.1 方案版本管理

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-40** | 大改（架构模式变更、`ServerType` 变更）→ 大版本 +1 | v1.0 → v2.0 |
| **OA-41** | 小改（扩缩容、新增 cmd、新增组件）→ 小版本 +0.1 | v1.0 → v1.1 |
| **OA-42** | 修正（勘误、补充说明）→ 修订号 +0.0.1 | v1.0 → v1.0.1 |

### 11.2 方案的向后兼容

| 编号 | 约束 | 说明 |
|------|------|------|
| **OA-43** | 新增 `ServerType` 不可回收已有值 | 即使原服务已废弃 |
| **OA-44** | 新增组件不可影响已有组件的生命周期时序 | 尤其注意 `MustRegister` 顺序 |
| **OA-45** | 容量规划变更必须重新评估所有关联服务 | 一个服务扩容可能导致下游瓶颈 |
