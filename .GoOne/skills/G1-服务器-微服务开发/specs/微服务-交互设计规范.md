# 微服务-交互设计规范

> 版本：v1.1
> 适用范围：所有基于 GoOne 框架（`lib/service/`）的微服务
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]]

---

## 一、规范定位

本规范定义了每个微服务在输出交互设计方案时必须达到的设计深度和质量标准。交互设计方案必须覆盖 C2S/S2C 协议、S2S 协议（ssrpc）、事件交互、完整业务流程时序和错误处理策略。

### 1.1 规范要求

交互设计方案必须覆盖以下 6 个维度：

| 维度 | 核心问题 | 不合格标准 |
|------|---------|-----------|
| **交互全景** | 服务与哪些外部系统有交互？方式是什么？ | 遗漏关键交互方或通信方式 |
| **C2S/S2C** | 每个客户端协议的定义是否完整？ | 缺少错误码、并发行为、异常处理 |
| **S2S（ssrpc）** | 每个服务间接口的定义是否完整？ | 缺少调用方权限、超时策略、降级方案 |
| **事件/通知** | 发布和订阅了哪些事件？ | 事件命名不规范、循环订阅未检查 |
| **流程时序** | 核心业务流程的跨服务交互是否清晰？ | 只有正常路径，没有异常路径 |
| **错误处理** | 所有异常场景是否都有处理策略？ | 只有"记录日志"，没有具体降级方案 |

## 二、交互全景标准

### 2.1 交互方穷举

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-01** | 必须列出所有与外部系统的交互 | Client、connsvr、其他服务、MySQL、Redis、bus（RabbitMQ） |
| **IA-02** | 每种交互必须标注通信方式和方向 | C2S / S2C 下行 / S2S ssrpc 调用 / S2S 接收 / 广播 |
| **IA-03** | 必须画出交互拓扑 ASCII 图 | 清晰展示服务在网络中的位置和连接关系 |
| **IA-04** | 交互汇总表必须包含预估频率 | 低频（每分钟 < 10 次）、中频、高频（每秒 > 100 次） |

### 2.2 交互全景检查

- [ ] Client、connsvr、MySQL、Redis、bus 的连接关系是否都已标注？
- [ ] 是否存在"绕过 connsvr 直连业务服务"的非法路径（web_svr 除外，它直接对外 HTTP/gRPC）？
- [ ] ssrpc 调用的方向是否正确（谁调谁）？
- [ ] 频率标注是否与容量规划一致？

## 三、C2S / S2C 协议设计标准

### 3.1 协议定义完备性

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-05** | 每个协议必须定义：触发条件、请求参数、响应参数、错误码 | 四要素缺一不可 |
| **IA-06** | 请求参数必须标注：类型、是否必填、取值范围 | 缺少范围会导致客户端发送非法值 |
| **IA-07** | 每个错误码必须有"客户端处理建议" | 开发不是错误码的使用者，客户端才是 |
| **IA-08** | 每个协议必须描述并发行为 | 重复发送：幂等/拒绝/允许？并发发送：serial key 串行化/允许？ |

### 3.2 协议时序要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-09** | 每个协议必须画出交互时序图 | 用 ASCII 时序图展示 Client ↔ connsvr ↔ 目标服务的消息流 |
| **IA-10** | 时序图必须标注关键处理步骤 | 参数校验 → 业务逻辑 → 数据持久化 → 响应 |
| **IA-11** | 如果涉及下行 Push/广播，必须在时序图中标注时机 | 是在响应之前还是之后推送？ |

### 3.3 下行 Push / 广播消息标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-12** | 下行消息必须定义触发条件 | 精确到哪个字段的哪种变更 |
| **IA-13** | 下行消息必须定义推送失败的处理策略 | 重试/忽略/记录日志/下次状态同步补偿 |
| **IA-14** | 下行消息必须有客户端处理建议 | 收到后客户端应如何更新 UI 或本地状态 |

> GoOne 的下行/广播经 connsvr 的 `ConnService`（`KickOut`/`Broadcast`）或下行 cmd（`SC_*`，ServerType=0）。

### 3.4 协议版本兼容

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-15** | 新增字段：老客户端不传时，服务端必须有默认值 | 否则老客户端请求报错 |
| **IA-16** | 废弃字段：使用 proto `reserved` 保留编号，不可删除 | 删除后编号可能被重用，导致协议错乱 |
| **IA-17** | 必须标注服务端各版本兼容的客户端版本范围 | 形成兼容矩阵 |

## 四、S2S（ssrpc）协议设计标准

### 4.1 接口定义完备性

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-18** | 每个 ssrpc 接口必须标注调用方和提供方 | 双向标注，不可只有一方 |
| **IA-19** | 调用方必须标注调用场景和触发条件 | "什么时候会调这个接口" |
| **IA-20** | 服务方必须描述完整的处理流程 | 校验 → 查找 → 处理 → 响应 |
| **IA-21** | ssrpc 接口的请求/响应参数必须与 C2S 同等标准定义 | 类型、必填、范围、说明 |

### 4.2 ssrpc 调用容错

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-22** | 所有 ssrpc 调用必须有超时设置 | 经 proto 的 `timeout_ms` 或 service 级 `ssrpc_service.timeout_ms` |
| **IA-23** | 非幂等 ssrpc 调用不可重试 | 重试可能导致重复扣款、重复发货 |
| **IA-24** | 幂等 ssrpc 调用最多重试 1 次 | 超过 1 次通常是下游问题 |
| **IA-25** | 必须定义目标服务不可达时的降级策略 | 返回缓存/默认值/报错给客户端 |

### 4.3 ssrpc 调用熔断

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-26** | 高频 ssrpc 调用必须设置熔断策略 | 连续失败 N 次 → 熔断 → 一段时间后尝试恢复 |
| **IA-27** | 熔断期间的降级行为必须明确定义 | 不能让用户感知到"系统故障" |
| **IA-28** | 熔断恢复后首次请求必须是探测性质的 | 避免恢复后立即被大量请求再次击垮 |

### 4.4 ssrpc 权限与安全

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-29** | 调用方身份必须可验证 | 通过 bus 的 BusId 与 ServerType 校验 |
| **IA-30** | ssrpc 消息中的 UID 必须校验 | 防止越权操作不属于该用户的数据（配合 `uid_lock` option） |

## 五、事件 / 通知交互标准

### 5.1 命名规范

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-31** | 事件/通知命名必须遵循 `{领域}:{动作}` 格式 | 如 `item:added`、`role:changed`、`room:finished` |
| **IA-32** | 事件类型必须在统一的常量位置定义 | 不可在组件内部硬编码字符串 |
| **IA-33** | 事件 Payload 必须定义明确的类型 | 不可以用 `interface{}`/`any` 且不加说明 |

### 5.2 订阅规范

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-34** | 所有订阅必须在 Component 生命周期内完成 | Start 阶段订阅，Stop 阶段退订 |
| **IA-35** | 必须检查事件订阅不会形成循环 | A 订阅 B 的事件并在处理中发布 B 会订阅的事件 |
| **IA-36** | 事件处理必须是非阻塞的 | 不允许在事件回调中做阻塞 DB 查询或网络 IO |

### 5.3 事件驱动流程

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-37** | 基于事件驱动的业务流程必须画出事件流转图 | 触发操作 → 事件A → 组件1处理 → 事件B → 组件2处理 |
| **IA-38** | 必须在流程中标注每一步是同步还是异步 | 经事务串行 vs 独立 goroutine（注意 `safego.Go`） |

## 六、业务流程时序标准

### 6.1 时序图要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-39** | 核心业务流程必须画出完整的跨服务时序图 | 至少覆盖 1-3 个核心业务场景 |
| **IA-40** | 时序图必须包含所有参与方 | Client → connsvr → 本服务 → 依赖服务（经 bus） |
| **IA-41** | 时序图必须同时展示正常路径和异常路径 | 只画成功路径的设计是不完整的 |

### 6.2 步骤描述要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-42** | 时序图的每个步骤必须有编号和文字说明 | 对应时序图中的箭头编号 |
| **IA-43** | 异常路径必须标注：哪个步骤可能失败、失败后如何处理 | 不能只说"步骤 3 可能失败" |

### 6.3 必须覆盖的核心流程

根据服务类型，至少覆盖以下业务场景的时序：

| 服务类型 | 必须覆盖的流程 |
|---------|-------------|
| 无状态服务 | 客户端请求 → connsvr → 服务处理 → 返回响应（含参数校验失败路径） |
| 无状态服务（有 ssrpc） | 客户端请求 → 本服务 → ssrpc 调用 → 返回（含超时降级路径） |
| 有状态服务 | 用户登录 → connsvr → mainsvr RoleMgr 加载 → 下行初始数据 |
| 有状态服务 | 客户端操作 → serial key 串行 → 组件交互 → 数据保存 → 下行 |
| 有状态服务 | 用户离线 → 数据保存 → 角色卸载 |

## 七、错误处理与降级策略标准

### 7.1 错误码设计

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-44** | 每个模块的错误码必须在独立号段内 | 定义在 `common/game_proto/core/error_code.proto` |
| **IA-45** | 错误码必须区分"客户端可修复"和"客户端不可修复" | 前者给用户提示后重试，后者提示稍后再试 |
| **IA-46** | 系统级错误（DB 超时、网络错误）统一使用通用错误码 | 不给客户端暴露内部细节 |

> GoOne 错误处理统一用 `lib/api/gerr`（或 ssrpc 的 `ssrpc.E`/`Wrap`），禁止 `rsp.Ret.Code = ERR_X` 后 `return rsp, nil`。

### 7.2 降级策略

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-47** | 必须定义每个 ssrpc 依赖不可用时的降级行为 | 不是"记录日志"就完事了 |
| **IA-48** | 降级策略必须保证核心功能可用 | 排行榜不可用时，基础游戏功能不能受影响 |
| **IA-49** | 降级期间的用户体验必须有明确说明 | 哪些功能按钮变灰？哪些数据展示为空？ |

### 7.3 客户端断线处理

| 编号 | 约束 | 说明 |
|------|------|------|
| **IA-50** | 无状态服务：客户端断线无影响 | 下次请求自动路由到可用实例 |
| **IA-51** | 有状态服务：客户端断线后角色行为必须明确定义 | 心跳淘汰间隔（`ClientExpiryThreshold = 6 × 心跳`）？重连后如何恢复？ |

## 八、文档质量标准

### 8.1 必须包含的章节

- [ ] 交互全景图（ASCII 拓扑图 + 交互汇总表）
- [ ] 所有 C2S/S2C 协议的详细定义（含错误码和异常处理）
- [ ] 所有下行 Push/广播消息的定义（含触发条件和失败处理）
- [ ] 所有 ssrpc 接口的详细定义（含容错、熔断、降级策略）
- [ ] 事件清单和事件驱动流程图
- [ ] 核心业务时序图（正常 + 异常路径）
- [ ] 协议版本兼容矩阵
- [ ] 设计检查清单

### 8.2 跨文档引用

交互设计方案必须引用：
- 整体设计方案（`ServerType`、cmd 号段、架构模式）
- 数据库设计方案（协议中涉及的数据读写对应的存储结构）
- 功能组件化规范（事件总线和组件间交互）
