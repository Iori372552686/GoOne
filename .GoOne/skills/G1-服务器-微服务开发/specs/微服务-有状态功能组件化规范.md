# 微服务-有状态功能组件化规范

> 版本：v1.1
> 适用范围：基于 GoOne 框架（`lib/service/`）的有状态微服务（Component + TransactionMgr serial key 模式）
> 参考实现：`src/mainsvr/`（RoleMgr + role 业务组件）、`src/roomcentersvr/`（RoomListMgr + 房间逻辑）
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]] | [[有状态微服务设计规范]]

---

## 一、规范定位

本规范定义了有状态微服务采用 Component + TransactionMgr sharded serial key 模式时必须遵循的组件化设计标准。核心目标：通过 Component 管理资源生命周期、通过 serial key 保证 key-local 串行、通过接口契约通信，确保组件可独立开发、独立测试、独立替换。

> ⚠️ GoOne **不使用 Actor 模型**。有状态串行化由 `lib/service/transaction` 的 sharded serial key 提供（按 UID/RouterID 分片串行），不是 Actor mailbox。

### 1.1 规范要求

功能组件化方案必须覆盖以下 6 个维度：

| 维度 | 核心问题 | 不合格标准 |
|------|---------|-----------|
| **组件架构** | 哪些是核心组件？哪些是扩展？决策依据是什么？ | 随意分类，无决策标准 |
| **接口契约** | 组件之间的通信接口是否清晰定义？ | 接口定义含混，依赖关系有循环 |
| **生命周期** | 每个阶段做什么？顺序是否合理？ | 阶段缺失，或时序有逻辑错误 |
| **路由注册** | 每个组件的 cmd 是否无冲突？ | 同一 cmd 被多个组件注册 |
| **事件设计** | 事件命名是否规范？订阅是否有循环？ | 事件命名随意，形成循环订阅 |
| **数据治理** | 每个组件如何持久化？落盘 hash field 是否唯一？ | field 冲突，数据互写 |

## 二、组件架构标准

### 2.1 组件分类决策

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-01** | 基础设施组件（EventBus、scheduler、Redis/ORM 依赖）最先 `MustRegister` | 其他组件在 Start 中就需要使用它们 |
| **SC-02** | 核心组件必须走分类决策：是否所有请求都需要？是否被其他核心组件依赖？| 两个条件都满足 → 核心组件 |
| **SC-03** | 扩展组件通过 `MustRegister` 注册 | 扩展组件可知可不存，不应影响核心功能 |
| **SC-04** | 核心组件必须暴露接口契约，扩展组件通过接口发现 | 类型安全 + 松耦合 |

### 2.2 组件依赖顺序

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-05** | 组件 Start 顺序必须遵循依赖关系 | DB 依赖先于业务组件，业务组件先于 TransMgr/Router |
| **SC-06** | 组件 Stop 顺序必须逆序 | 后 Start 的先 Stop，避免悬空引用 |
| **SC-07** | 禁止组件在未完成 Start 的情况下被调用 | `Ready` 状态前任何组件不应被外部调用 |

### 2.3 参考实现

| 服务 | 核心结构 | 说明 |
|------|---------|------|
| mainsvr | `RoleMgr` + `roleTick`（定时落盘）+ `roleFlushComponent`（Drainer）+ `selfLogout` | 玩家按 UID 串行，定时落 Redis hash |
| roomcentersvr | `RoomListMgr` + `roomTick`（5s）+ `roomPersist`（10s）+ `roomFlushComponent`（Drainer）+ `room_ai` | 房间按 RouterID 串行，`MaxPendingPerKey=200` |

## 三、组件接口设计标准

### 3.1 Component 接口（`lib/service/runtime/component.go`）

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-08** | 组件必须实现 `Name() / Start(ctx) / Stop(ctx)` | 框架调度的最低契约 |
| **SC-09** | 需要停机落盘的组件实现 `Drainer`（`Drain(ctx)`） | 如 mainsvr `roleFlushComponent`、roomcentersvr `roomFlushComponent` |
| **SC-10** | 需要停止接新请求的组件实现 `Quiescer`（`Quiesce(ctx)`） | 如 router `RouterComponent` |

### 3.2 事件总线接口

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-11** | 事件总线必须提供 Subscribe / Unsubscribe / Publish 三方法 | 最小完备接口 |
| **SC-12** | 事件必须包含 Type（事件类型字符串）和 Data（事件数据）字段 | Type 用于路由分发 |
| **SC-13** | 事件发布必须是同步广播 | 在发布者 goroutine 中遍历所有订阅者并调用 handler |
| **SC-14** | 禁止在事件回调中做阻塞操作 | 同步广播 + 阻塞 = 发布者被无限阻塞 |

## 四、路由（ssrpc）注册标准

### 4.1 注册机制

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-15** | ssrpc handler 经 `ssrpc.NewRegistryComponent` + `Register<Svc>ToRegistry` 注册 | CI 门禁禁止 `RegisterXxxToDispatcher`/`TransMgr.RegisterCmd` |
| **SC-16** | 同一 cmd 只能被一个 handler 注册 | 路由冲突会导致不可预期的行为 |
| **SC-17** | `RegistryComponent` 配 `WithTransactionManager(globals.TransMgr)` | handler 经 TransMgr sharded 分发 |

### 4.2 serial key 约束

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-18** | handler 必须保持 key-local（同一 UID/RouterID 串行） | TransactionMgr 按 RouterID/Uid 分片串行 |
| **SC-19** | 禁止依赖全局单线程排序 | 不同 key 的 handler 可能并发执行 |
| **SC-20** | 高频同键场景可覆盖 `MaxPendingPerKey`（如 roomcentersvr=200） | 默认 100 |

## 五、跨组件通信标准

### 5.1 通信方式选择

| 场景 | 推荐方式 | 理由 |
|------|---------|------|
| 需要同步返回结果 | 通过接口直接调用 | 同一 serial key 内安全 |
| 状态变更通知（不期待返回值） | 通过 EventBus 发布事件 | `EventBus.Publish(EventRoleChanged)` |
| 客户端请求驱动 | ssrpc handler | 经 Dispatcher 路由到 handler |

### 5.2 接口契约标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-21** | 核心组件必须暴露类型安全的接口 | 方便其他组件调用 |
| **SC-22** | 接口方法必须明确表达意图和副作用 | `AddItem` 意味着会产生变更，`QueryItems` 意味着只读 |
| **SC-23** | 禁止组件直接持有其他组件的实例指针 | 通过接口访问，避免形成硬依赖 |

### 5.3 事件设计标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-24** | 事件命名必须遵循 `{领域}:{动作}` 格式 | 如 `item:added`、`role:changed` |
| **SC-25** | 事件类型常量必须在统一的文件中定义 | 不可在组件内部硬编码字符串 |
| **SC-26** | 禁止事件循环：A 事件的处理中不可发布 A 事件 | 会导致无限递归，stack overflow |
| **SC-27** | 订阅的句柄必须保存，在 `Stop` 中退订 | 否则组件 Stop 后事件总线仍有引用 |

## 六、数据持久化标准

### 6.1 落盘 hash field 分配（mainsvr Redis hash）

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-28** | 每个业务模块必须有唯一的 Redis hash field | 在 `persist_hash.go` 编排中不重复 |
| **SC-29** | 组件只能读写自己的 field | 不可跨 field 读写其他组件的数据 |
| **SC-30** | field 一旦分配不可回收 | 即使组件废弃，其 field 也不可被其他组件使用 |

### 6.2 持久化策略

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-31** | 关键数据（货币、道具）必须先落库再更新内存 | 防止宕机导致数据丢失 |
| **SC-32** | 普通数据（属性等）可以先更新内存并标记脏数据，定时回写 | 性能优先，容忍少量数据丢失 |
| **SC-33** | 必须设置定时落盘 Component（建议 ≤ 60s） | 如 mainsvr `roleTick` 每分钟 |
| **SC-34** | 必须装配停机 Drainer 全量落盘 | 如 mainsvr `roleFlushComponent` |

## 七、组件测试标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **SC-35** | 每个组件必须有独立的单元测试文件 | `{组件名}_test.go`，放在组件同目录下 |
| **SC-36** | 测试必须构造完整的依赖桩 | 提供所有必要的基础设施：EventBus、scheduler、Redis mock |
| **SC-37** | 必须覆盖正常路径 + 异常路径 | 正常加载、空数据加载、落盘失败、并发冲突 |
| **SC-38** | 集成测试经 `lib/internal/itest`（`GOONE_INTEGRATION=1`） | 中间件不可达必须 `t.Fatal` |

## 八、文档质量标准

### 8.1 必须包含的章节

- [ ] 组件架构总览图（服务 → 核心组件 → 扩展组件 → 子系统）
- [ ] 核心组件清单（名称、职责、接口、落盘 field）
- [ ] 扩展组件清单（名称、职责、注册方式）

- [ ] 组件依赖关系图（禁止循环依赖）

- [ ] 设计检查清单

### 8.2 跨文档引用

功能组件化方案必须引用：
- 整体设计方案（服务定位、架构模式）
- 数据库设计方案（落盘结构，见 `.GoOne/spec/03`）
- 交互设计方案（组件注册的 cmd 对应的协议）
