# 微服务-无状态功能组件化规范

> 版本：v1.1
> 适用范围：基于 GoOne 框架（`lib/service/`）的无状态微服务（Component 模式）
> 设计目标：通过 Component 注册监听 cmd，通过服务内事件派发机制完成组件交互，实现组件内业务解耦
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]] | [[无状态微服务设计规范]]

---

## 一、规范定位

本规范定义无状态微服务采用 Component 模式时必须遵循的组件化设计标准。核心目标：将无状态服务中集中式的 cmd 分发改造为组件自治注册，用服务级事件总线替代直接耦合，使每个组件可独立开发、独立测试、可按需启用或关闭。

### 1.1 与有状态组件化的本质差异

无状态组件化不维护玩家在线状态和数据缓存，核心在于**路由解耦**和**事件解耦**：

| 关注点 | 有状态（mainsvr RoleMgr + Component） | 无状态（Component） |
|--------|--------------------------------------|---------------------|
| 持久化 | Role 管理数据，定时落 Redis hash | 组件直接通过 `lib/db/redis` 或 ssrpc 读写 |
| 生命周期 | Component 的 Start/Stop（+ Role 的加载/落盘） | Component 的 Start/Stop |
| 事件作用域 | 同一 serial key 内（单玩家） | 同一服务实例内（多玩家共享） |
| 并发模型 | TransactionMgr sharded serial key（按 UID/RouterID 串行） | 请求级 goroutine 并发 |

### 1.2 规范要求

功能组件化方案必须覆盖以下 6 个维度：

| 维度 | 核心问题 | 不合格标准 |
|------|---------|-----------|
| **组件架构** | 服务如何持有和管理组件？ | 服务与组件的关系不清晰 |
| **接口契约** | 组件间如何通信？用什么接口？ | 通信方式没有标准，随意耦合 |
| **路由注册** | 每个组件的 cmd 是否无冲突？ | 同 cmd 被多组件注册 |
| **事件设计** | 事件总线设计是否线程安全？ | EventBus 在多 goroutine 下不安全 |
| **并发安全** | 并发请求下组件状态如何保护？ | 共享数据无并发保护 |
| **生命周期** | 组件初始化/销毁的顺序和时机？ | 启动时组件未就绪就接收请求 |

## 二、Component 容器设计标准

### 2.1 Component 接口（`lib/service/runtime/component.go`）

GoOne 的 Component 是框架级标准接口：

```go
type Component interface {
    Name() string
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
}
// 可选扩展
type Quiescer interface{ Quiesce(ctx context.Context) error }
type Drainer interface{ Drain(ctx context.Context) error }
```

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-01** | 组件必须实现 `Component` 三方法（Name/Start/Stop） | 框架调度的最低契约 |
| **NS-02** | 组件经 `app.MustRegister(...)` 注册 | 注册顺序即 Start 顺序；Stop 逆序 |
| **NS-03** | 需要排空在途请求的组件实现 `Drainer` | 停机时 Drain 先于 Stop |
| **NS-04** | 闭包式组件用 `bussvc.FuncComponent` | 把任意 `OnStart`/`OnStop` 闭包适配为 Component |

### 2.3 组件分类标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-05** | 基础设施组件（EventBus、Timer/scheduler）最先注册 | 其他组件在 Start 中就需要使用 |
| **NS-06** | 核心业务组件直接作为字段声明在装配结构中 | 被多个组件依赖的组件必须能快速访问 |
| **NS-07** | 扩展组件通过 `MustRegister` 注册 | 可选功能，不注册不影响核心业务 |
| **NS-08** | 核心业务组件必须暴露接口契约 | 方便其他组件类型安全地调用 |

### 2.4 服务初始化标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-09** | 初始化必须分阶段：基础设施 → 核心业务 → 扩展 | `MustRegister` 顺序不可乱 |
| **NS-10** | 必须在所有组件 Start 完成后（`Ready`）才接收请求 | 否则请求可能到达未初始化的组件 |
| **NS-11** | `Start` 返回 nil 即可用，失败须自行清理 | App 不调 Stop（见 `docs/STYLE.md` P0 生命周期） |

## 三、路由（ssrpc）注册标准

### 3.1 注册机制

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-12** | ssrpc handler 经 `ssrpc.NewRegistryComponent` + `Register<Svc>ToRegistry` 注册 | CI 静态门禁禁止 `RegisterXxxToDispatcher`/`TransMgr.RegisterCmd` |
| **NS-13** | 同一 cmd 只能被一个 handler 注册 | 冲突会导致不可预期的行为 |
| **NS-14** | cmd 分配遵循 `ServerType` 号段表 | 见 [02-通讯协议规范文档.md](../../spec/02-通讯协议规范文档.md) |

```go
// src/<svc>svr/app.go
registerHandlers := ssrpc.NewRegistryComponent(
    "ssrpc_registry",
    func(r *ssrpc.Registry) error {
        srv := <svc>v1.New<Svc>SServer(&service.Impl{}, ssrpc.DefaultMWOptions{})
        return <svc>v1.Register<Svc>ToRegistry(r, srv)
    },
    ssrpc.WithTransactionManager(globals.TransMgr),
)
```

### 3.2 路由去中心化要求

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-15** | 禁止在核心代码中 switch-case 按 cmd 分发 | ssrpc Dispatcher 自动按 cmd 路由到 handler |
| **NS-16** | 新增组件不应修改已有组件的注册代码 | 每个组件只关心自己的 cmd |

## 四、事件总线标准

### 4.1 接口要求

事件总线是服务内组件交互的核心机制，必须满足：

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-17** | 必须提供 Subscribe（订阅）、Unsubscribe（退订）、Publish（发布）三方法 | 最小完备接口 |
| **NS-18** | Subscribe 和 Publish 必须是并发安全的 | 多 goroutine 可能同时订阅和发布 |
| **NS-19** | 事件发布是同步的：在当前 goroutine 中遍历所有订阅者 | 发布者可以感知订阅者的处理结果 |
| **NS-20** | 订阅者的事件处理必须是轻量的、非阻塞的 | 同步广播 + 阻塞 = 发布者被无限阻塞 |

### 4.2 事件设计规范

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-21** | 事件命名必须遵循 `{领域}:{动作}` 格式 | 如 `match:found`、`room:closed`、`role:finished` |
| **NS-22** | 事件类型字符串必须在统一位置定义 | 不可在组件内硬编码，否则重构时遗漏 |
| **NS-23** | 事件 Data 必须是值类型或不可变对象 | 传递可变引用会导致竞态条件 |
| **NS-24** | 禁止事件循环 | 在处理事件 A 的回调中不可发布事件 A |
| **NS-25** | 所有订阅句柄必须在 `Stop` 中退订 | 否则服务关闭时 EventBus 仍有悬空引用 |

### 4.3 事件 vs 接口调用选择

| 场景 | 推荐方式 | 理由 |
|------|---------|------|
| 状态变更通知（多组件需要知道） | EventBus.Publish | 松耦合，新订阅者无需修改发布者 |
| 同步获取结果 | 组件接口直接调用 | 事件不支持返回值 |
| 跨组件协作（A 触发 B 的动作） | EventBus.Publish + B 订阅 | B 的变更不影响 A |

## 五、并发安全标准

无状态服务的组件在多个 goroutine 中并发处理请求，这是与有状态 serial key 串行的最本质差异。

### 5.1 共享数据保护

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-26** | 组件内所有共享数据必须用 sync.Mutex 或 sync.RWMutex 保护 | 不可假设单线程访问 |
| **NS-27** | EventBus 的订阅者列表必须用 sync.RWMutex 保护 | Subscribe/Unsubscribe 可能在业务请求 goroutine 中发生 |
| **NS-28** | 定时器回调在独立 goroutine 中，访问共享数据必须加锁 | 或经事务投递到安全的执行上下文 |

### 5.2 禁止的并发模式

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-29** | 禁止在组件内使用 map 不加锁 | Go 的 map 并发写会 panic |
| **NS-30** | 禁止假设请求的处理顺序 | 不同 goroutine 中并发执行 |
| **NS-31** | 禁止在事件回调中做阻塞 IO | 所有订阅者被阻塞，服务吞吐量暴跌 |

## 六、定时任务标准

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-32** | 定时器复用 `lib/service/scheduler`（`scheduler.New(name, period, fn)`） | 默认 NonOverlap（禁止重入） |
| **NS-33** | 定时器回调在独立 goroutine 中执行 | 不是请求处理 goroutine |
| **NS-34** | `Stop` 必须取消所有定时器 | 避免 Service 关闭后定时器仍在执行 |
| **NS-35** | select 禁用 `time.After` | 用 `time.Timer` 复用（`docs/STYLE.md`） |

## 七、组件生命周期标准

### 7.1 完整时序（runtime 状态机）

```
Starting → Ready → (Allocated) → Draining → Stopping → Stopped / Failed
```

- `MustRegister` 顺序即 Start 顺序
- Quiesce 先于 Drain 先于 Stop
- Stop 按注册**逆序**
- `Start` 返回 nil 即可用，失败自行清理（App 不调 Stop）
- `Stop` 幂等

### 7.2 生命周期约束

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-36** | `Start` 阶段只能做初始化，不能做长时间阻塞 IO | 阻塞服务启动 |
| **NS-37** | `Stop` 必须退订所有事件、取消所有定时器 | 否则服务关闭后仍有 goroutine 运行 |
| **NS-38** | 组件 Stop 顺序必须与注册顺序相反 | 先注册的后 Stop，避免悬空引用 |

## 八、跨组件通信标准

### 8.1 接口契约

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-39** | 核心组件必须暴露接口，提供服务级快捷访问 | 经 globals 或装配结构体访问 |
| **NS-40** | 禁止组件直接持有其他组件的指针 | 通过接口访问，避免硬依赖 |
| **NS-41** | 跨服务调用经 ssrpc client，禁止绕过 | `<svc>v1.New<Svc>Client().Method(trans, &req)` |

### 8.2 组件可替换性

| 编号 | 约束 | 说明 |
|------|------|------|
| **NS-42** | 核心组件实现对应接口后，可替换为 mock 实现用于测试 | 测试时注入 mock 组件 |
| **NS-43** | 扩展组件的注册/注销不应影响核心组件运行 | 扩展组件故障不应导致服务不可用 |

## 九、文档质量标准

### 9.1 必须包含的章节

- [ ] 组件架构总览（服务 → 核心组件 → 扩展组件）
- [ ] 核心组件清单（名称、职责、接口、事件订阅/发布）
- [ ] 扩展组件清单（名称、职责、注册方式）
- [ ] 事件清单（事件名、Payload 类型、发布者、订阅者）
- [ ] 组件依赖关系图（禁止循环依赖）
- [ ] 并发安全分析（每个共享数据的保护方式）
- [ ] 设计检查清单

### 9.2 跨文档引用

功能组件化方案必须引用：
- 整体设计方案（服务定位、架构模式）
- 数据库设计方案（组件读写的 Redis key / MySQL 表）
- 交互设计方案（组件注册的 cmd 对应的协议）
