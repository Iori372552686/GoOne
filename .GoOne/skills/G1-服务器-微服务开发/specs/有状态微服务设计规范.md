# 有状态微服务设计规范

> 版本：v1.1
> 适用范围：所有基于 GoOne 框架（`lib/service/`）的有状态微服务（Component + TransactionMgr sharded serial key 模式）
> 相关文档：[[../SKILL.md|G1-服务器-微服务开发]]

---

## 一、有状态服务的定义

有状态微服务是指**将用户/房间数据加载到进程内存，通过 TransactionMgr sharded serial key 保证 key-local 串行化处理，按 UID/RouterID 路由到固定实例**的服务。在 GoOne 框架中，这类服务通过 `SvrRouterRule_Hash_UID`（按玩家）或 `SvrRouterRule_Hash_RouterID`（按房间）实现粘性路由。

> ⚠️ GoOne **不使用 Actor 模型 / Actor mailbox / Locator**。串行化由 `lib/service/transaction` 的 sharded serial key 提供。

### 1.1 框架层特征

| 特征 | 取值 |
|------|------|
| 路由规则 | `SvrRouterRule_Hash_UID`（按玩家）或 `SvrRouterRule_Hash_RouterID`（按房间/RouterID） |
| UID/RouterID 依赖 | 必须（参与路由分片） |
| 并发模型 | TransactionMgr sharded：请求按 RouterID/Uid 串行键分片，同 key 串行，跨 key 并发 |
| Shard 数 | 固定 `DefaultShardCount()`（基于 GOMAXPROCS，上限 32），不可外部调参 |
| 同键 backpressure | 默认 `DefaultMaxPendingPerKey = 100`；roomcentersvr 覆盖为 200 |
| 典型服务 | mainsvr（玩家）、infosvr（玩家缓存）、mysqlsvr/roomcentersvr（RouterID） |

### 1.2 消息流路径

```
Client → connsvr → router(按 cmd 的 ServerType + ServerRouteRules=Hash_UID/Hash_RouterID)
                                       ↓
                                 选定固定实例（按 uid/routerID 取模）
                                       ↓
                                 globals.TransMgr（sharded）
                                       ↓
                                 按 RouterID/Uid 分片 → 同 key 串行队列
                                       ↓
                                 ssrpc Dispatcher → middleware → handler
                                       ↓
                                 操作内存数据（RoleMgr / RoomListMgr）
                                       ↓
                                 定时落盘（roleTick / roomPersist）+ 停机 Drainer
```

### 1.3 serial key 线程模型

```
TransactionMgr shard（按 (RouterID 或 Uid) hash 分片）
    │
    ├── 同 key 串行队列（容量 = MaxPendingPerKey）
    │       └── handler(ctx) → 操作该 key 的内存数据
    │
    └── 不同 key 并发（不同 goroutine）
```

- 同一 UID/RouterID 的所有请求严格串行（无需额外锁）
- 不同 UID/RouterID 的请求可并发（handler 内的共享数据仍需保护）

## 二、架构约束（强制标准）

### 2.1 路由约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **S-01** | 必须使用 `Hash_UID` 或 `Hash_RouterID` 路由规则 | 不用则请求路由到不同实例，无法保证 key-local |
| **S-02** | handler 必须保持 key-local | 同一 key 的状态依赖才能成立 |
| **S-03** | 禁止依赖全局单线程排序 | 不同 key 的 handler 可能并发 |

### 2.2 数据约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **S-04** | 必须装配定时落盘 Component（间隔 ≤ 1 分钟） | 节点宕机丢失最后一次落盘后的增量 |
| **S-05** | 必须装配停机 Drainer 全量落盘 | 优雅停机时数据丢失 |
| **S-06** | 关键写操作（货币、道具）必须先落库再更新内存 | 宕机时内存数据丢失但库已写入 |
| **S-07** | 数据读写通过 `lib/db/redis` 或 ssrpc | 绕过接口无法利用连接池 |
| **S-08** | handler 内禁止与后台 goroutine 共享可变对象 | 数据竞争（参考 `SelfLogoutSender` 模式：经事务串行化） |

### 2.3 Component 生命周期约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **S-09** | 必须实现 `Component` 的 `Name/Start/Stop` | 框架调度链断裂 |
| **S-10** | 需要停机落盘的组件必须实现 `Drainer` | 数据丢失（如 `roleFlushComponent`） |
| **S-11** | `Start` 返回 nil 即可用，失败自行清理 | App 不调 Stop |
| **S-12** | `Stop` 幂等 | 重复调用不出错 |
| **S-13** | 状态机：`Starting→Ready→(Allocated)→Draining→Stopping→Stopped/Failed` | Quiesce 先于 Drain 先于 Stop |

### 2.4 消息处理约束

| 编号 | 约束 | 违规后果 |
|------|------|---------|
| **S-14** | handler 必须非阻塞（禁止阻塞 IO 拖慢 serial key 队列） | 同 key 的所有后续请求被阻塞 |
| **S-15** | 需要阻塞 IO 的操作异步化或经事务投递 | serial key 队列积压 |
| **S-16** | 同一 UID/RouterID 的核心数据必须聚合在同一服务 | 数据分散导致一致性问题 |

## 三、生命周期管理

### 3.1 完整生命周期流程（mainsvr 参考）

```
服务启动 bussvc.MustNew("mainsvr", ...)
    ↓
MustRegister（顺序即 Start 顺序）:
  1. businessDeps（敏感词、Redis、IDGen、gamedata）— FuncComponent
  2. selfLogout（注入 role.SelfLogoutSender）
  3. registerHandlers（ssrpc RegistryComponent）
  4. roleTick（scheduler.New("role_tick", 1m, RoleMgr.Tick)）
  5. transMgr（TransMgrComponent，Drainer）
  6. roleFlushComponent（Drainer，停机全量落盘）
  7. routerComp（RouterComponent，Quiescer）
    ↓
状态：Ready → 接收请求
    ↓
... 运行中（RoleMgr 管理在线角色，roleTick 每分钟落盘）...
    ↓
优雅停机（逆序）:
  1. routerComp.Quiesce（停止接新请求，readyz=503）
  2. roleFlushComponent.Drain（全量 SaveToDBSync）
  3. transMgr.Drain（排空在途事务）
  4. ... 各组件 Stop（逆序）
  5. 状态：Stopped
```

### 3.2 必须维护的状态清单

| 状态 | 类型 | 初始化 | 清理 |
|------|------|--------|------|
| 角色实例池 | `RoleMgr` 内部 map | 登录时创建 | 离线/停机时落盘后释放 |
| 内存数据 | Role 结构体 | 从 Redis hash 加载 | 落盘后释放 |
| 脏标记 | Role 内部 | 写入时标记 | 落盘后清除 |
| 定时器 | `scheduler.Task` | Start 时注册 | Stop 时取消 |
| 在线标记 | Role 内部 | 上线后置 true | 离线后置 false |

## 四、数据持久化策略

### 4.1 写入策略选择

| 数据类别 | 策略 | 写入时机 | 示例 |
|---------|------|---------|------|
| **关键数据** | 先落库 → 再更新内存 | 每次操作后立即 | 货币、道具、支付 |
| **普通数据** | 先更新内存 → 定时批量回写 | 定时器触发 + 离线触发 | 属性等 |
| **实时计数器** | Redis 原子操作 | 每次操作 | 排行榜分数 |
| **日志/记录** | 经 mysqlsvr 异步写 | 每次操作后 | 对局记录（Texas 三表） |

### 4.2 定时保存策略（mainsvr 参考）

```
落盘触发条件（任一满足即触发）:
  1. roleTick 定时器到期（每分钟，RoleMgr.Tick）
  2. 用户离线（心跳超时，ClientExpiryThreshold = 6 × 心跳）
  3. 节点停机（roleFlushComponent.Drain）

落盘内容:
  1. 按模块增量写 Redis hash（saveRoleHash，只写脏 field）
  2. 关键字段经 ssrpc 调 mysqlsvr 落 MySQL（SaveToMysql）

落盘失败处理:
  1. 记录错误日志
  2. 保留脏标记，下次定时器触发时重试
  3. 连续失败 → 告警
```

### 4.3 数据加载策略

```
首次加载（用户登录）:
  1. mainsvr RoleMgr 从 Redis hash 加载完整用户数据（反序列化各模块）
  2. 数据不存在 → 创建默认数据（首次登录）

热加载（用户重连）:
  1. 检查 Role 是否已在内存（同一实例，因 Hash_UID 粘性）
  2. 存在 → 复用内存数据
  3. 不存在（如实例重启后）→ 重新从 Redis 加载
```

## 五、优雅下线策略

### 5.1 下线流程（runtime 状态机）

```
1. 状态切换：Ready → Draining
   - RouterComponent.Quiesce：停止接新请求
   - readyz 返回 503，healthz 仍 200

2. Drainer.Drain（逆序）:
   - roleFlushComponent：遍历所有在线 Role，全量 SaveToDBSync
   - transMgr：排空在途事务
   - （connsvr 等网关：SessionTracker.WaitSessions 等待在途会话）

3. 状态切换：Draining → Stopping → Stopped
   - 各组件 Stop（逆序）
   - 解注册服务实例
```

### 5.2 下线时间预估

```
下线时间 ≈ 单角色 Save 时间 × 在线角色数 + Drain 排空时间

单角色 Save 时间: ~5-20ms（Redis hash 写入）
1000 在线角色: 5-20s 下线时间

建议: 提前通知所有玩家（"服务器即将维护"），
      给玩家充足时间完成当前操作后再执行下线。
```

## 六、容量规划标准

### 6.1 单节点容量公式

```
单节点最大在线 = 节点可用内存 × 0.7 / 单玩家平均内存

节点可用内存 = 总内存 - 系统开销(1GB) - Go 运行时开销(500MB)

示例:
  16GB 节点，单玩家 500KB:
    最大在线 = (16 - 1.5) × 1024 × 1024 / 500 ≈ 30,000
  实际建议: 不超过 10,000 在线（预留 GC 空间和突发流量）
```

### 6.2 单玩家内存构成

| 组成部分 | 典型大小 | 说明 |
|---------|---------|------|
| 玩家数据（Redis 加载到内存） | 50-500 KB | 属性、道具等 protobuf 数据 |
| 运行时索引 | +20% | Go map/slice 开销 |
| 组件缓存 | 10-200 KB | 配置表缓存、计算结果 |
| **合计** | **80-900 KB** | — |

### 6.3 节点数规划

```
所需节点数 = ceil(峰值在线 / 单节点最大在线 × 1.3)
冗余系数 1.3: 预留 30% 容量应对突发

示例:
  峰值在线 = 50,000，单节点最大 = 5,000
  所需节点数 = 50,000 / 5,000 × 1.3 = 13 台
```

### 6.4 DAU 与 PCU 换算

```
PCU（峰值同时在线）= DAU × 在线率 × 峰值集中系数

典型在线率: 休闲 5-8%、中重度 8-15%、MMO 15-25%
峰值集中系数: 1.2 - 1.5

示例: DAU=100万，在线率=10%，集中系数=1.3 → PCU=13万
```

## 七、组件化设计规范

### 7.1 组件接口标准

有状态服务推荐采用**组件化架构**，将不同业务模块拆分为独立 Component（见 [有状态功能组件化规范](微服务-有状态功能组件化规范.md)）。

### 7.2 组件间通信约束

| 编号 | 约束 | 说明 |
|------|------|------|
| **S-17** | 组件间只能通过接口交互 | 不能直接持有其他组件的指针 |
| **S-18** | 组件间数据传递使用值拷贝 | 避免共享可变状态 |
| **S-19** | 组件间事件通过 EventBus 中转 | 解耦组件依赖 |

## 八、故障恢复

### 8.1 节点宕机

```
检测: 注册中心（zk/etcd）lease 过期 → 服务实例下线
影响: 宕机节点上所有内存数据丢失（未落盘的增量丢失）
恢复:
  1. 用户下次请求到达 connsvr
  2. router 发现目标实例不可达，按 Hash_UID 重新选可用实例
  3. 新实例 RoleMgr 从 Redis hash 加载角色 → 继续服务
  4. 丢失数据 = 最后一次落盘到宕机之间的增量
```

### 8.2 数据恢复

```
增量数据丢失的处理:
  - 货币/道具（先落库策略）: 不丢失
  - 普通属性（定时落盘）: 丢失最后一次落盘后的增量
  - Redis 计数器: 不丢失（Redis 独立部署）

降低丢失风险的策略:
  1. 缩短落盘间隔（如 30s）
  2. 关键操作立即落盘
  3. 监控落盘成功率
  4. 多实例冗余部署
```

## 九、性能优化指南

### 9.1 内存优化

| 策略 | 效果 | 代价 |
|------|------|------|
| 字段按需加载 | 减少 30-50% 内存 | 访问时可能需 Redis 加载 |
| 大字段分离存储 | 减少热数据内存 | 需要额外的查询 |
| LRU 缓存淘汰 | 控制峰值内存 | 缓存未命中时性能下降 |

### 9.2 落盘优化

| 策略 | 效果 | 代价 |
|------|------|------|
| 增量落盘（只写脏 field） | 减少 70-90% 写入量 | 需要维护脏标记 |
| 合并落盘（多个变更一次写入） | 减少 Redis 连接占用 | 断电风险略微增加 |
| 异步落盘 | 不阻塞 serial key | 宕机可能多丢失一个批次 |

## 十、设计检查清单

### 启动前检查

- [ ] 路由规则：`Hash_UID` / `Hash_RouterID` □
- [ ] Component 生命周期：Name/Start/Stop 全部实现 □
- [ ] 定时落盘：间隔 ≤ 60s，逻辑完整 □
- [ ] 停机 Drainer：全量落盘 Component 已装配 □
- [ ] 关键写操作：先落库再更新内存 □
- [ ] serial key：handler 保持 key-local □
- [ ] handler 非阻塞：无阻塞 IO □
- [ ] 容量规划：已按 PCU 目标计算节点数 □

### 运行时检查

- [ ] 角色数：未超过单节点容量上限 □
- [ ] 内存使用：在预估范围内 □
- [ ] 落盘成功率：> 99.9% □
- [ ] 落盘延迟：P99 < 100ms □
- [ ] serial key 队列：未达 MaxPendingPerKey □

### 禁止模式检查

- [ ] 不存在 handler 内阻塞 IO（S-14） □
- [ ] 不存在 handler 与后台 goroutine 共享可变对象（S-08） □
- [ ] 不存在绕过 `lib/db/redis` 直接操作第三方存储 □
- [ ] 不存在同一 UID 核心数据分散多服务（S-16） □

## 十二、常见反模式与纠正

| 反模式 | 表现 | 纠正 |
|--------|------|------|
| "不落盘" | 没有定时落盘，只在停机时落 | 增设定时 Component，间隔 ≤ 60s |
| "全量落盘" | 每次落盘保存全部字段 | 改为增量，只写脏 field |
| "锁竞争" | 多个 goroutine 通过 sync.Mutex 访问同一 key 数据 | 利用 serial key 串行化（同 key 天然串行） |
| "跨 key 同步等待" | handler A 等 handler B 的结果 | 改为事件驱动或异步回调 |
| "handler 阻塞" | handler 内做阻塞 IO 拖慢 serial key 队列 | 异步化或经事务投递 |
| "共享可变对象" | handler 与后台 goroutine 共享数据 | 经事务串行化（`SelfLogoutSender` 模式） |
