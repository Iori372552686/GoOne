# G1-服务器-代码测验

## 概述

本技能在**业务代码开发完成并通过编译**后，基于 PRD、需求分析报告和技术分析方案，对已实现的业务代码进行**全方位代码测验**。核心目标：在代码提交联调之前，系统性地找出业务代码中的 **BUG、逻辑漏洞、数据不一致、边界缺失**。

> **定位**：
> - ✅ 基于 PRD + 需求分析报告 + 技术分析方案设计测试用例
> - ✅ 验证通讯协议接口的可靠性、异常处理、幂等、并发
> - ✅ 验证数据存储结构的一致性与读写正确性
> - ✅ 验证配置表加载、解析、关联关系
> - ✅ 基于需求分析报告中识别的边界条件展开覆盖
> - ✅ 对组件化架构（有状态 Actor-Component / 无状态 Service-Component）专项测验
> - ✅ 输出问题清单和测试报告
> - ❌ 不涉及需求审查、技术方案设计、业务编码开发

## 前置条件

1. `{analysis_output_dir}/{需求名称}/需求分析报告.md` 已存在且审查通过
2. `{analysis_output_dir}/{需求名称}/技术分析方案.md` 已存在且状态为"已确认"
3. `{analysis_output_dir}/{需求名称}/需求开发报告.md` 已存在
4. 业务代码已通过编译（`go build ./...` 无错误）

## 规范遵循（强制）

> 在验证配置表、通讯协议、数据库存储时，**先去 `.GoOne/spec/` 目录下自行寻找并读取相关规范文档**，确保被测实现遵循其中的规则和约定。测试用例的预期结果以规范为准。技能不固化具体规范文件名，以目录下实际文档为准。
>
> 对组件化架构的测验，**先阅读本技能 `specs/` 目录下的对应规范**：
> - 有状态服务（Actor-Component 模式）：[specs/有状态微服务组件模块的测验规范.md](specs/有状态微服务组件模块的测验规范.md)
> - 无状态服务（Service-Component 模式）：[specs/无状态微服务功能模块的测验规范.md](specs/无状态微服务功能模块的测验规范.md)

## 工作流程

### 第一步：获取项目配置 + 拉取输入文档

调用 `G1-项目配置` 技能获取配置。通过 obsidian-cli 拉取以下文档：

1. **PRD 文档**：明确需求的业务规则和预期行为
2. **需求分析报告**：提取逻辑闭环问题、边界条件问题、时序因果问题（**这些就是测验的核心目标**）
3. **技术分析方案**：提取配置表清单、通讯协议清单、数据存储结构、风险清单
4. **需求开发报告**：提取代码变更清单（哪些文件被修改/新增）

### 第二步：划定测验范围

从输入文档中提取以下四类测验范围：

| 范围 | 提取来源 | 核心关注 |
|------|---------|---------|
| **通讯协议接口** | 技术方案 → 协议清单 | 每个协议的 Req/Rsp/Push，方向，所属服务，CMD 常量 |
| **数据存储结构** | 技术方案 → 存储设计 | MySQL 表/Redis Key 模板、字段结构 |
| **配置表** | 技术方案 → 配置表清单 | Proto 文件、JSON 路径、表间关联关系 |
| **业务边界** | 需求分析报告 → 边界/时序/状态机问题 | 数值边界、集合边界、时间边界、非法流转 |
| **组件架构** | 代码结构（根据服务类型选择对应规范） | 核心/扩展组件划分、接口契约、生命周期、事件 |

### 第三步：通用四维测验

#### 维度 1：通讯协议接口测验

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **正常流程** | 请求能正确处理并返回预期结果 | 构造正常参数调用，验证响应码和数据 |
| **异常参数** | 非法参数不会导致 crash | 零值、负数、超大值、空字符串、缺失必填字段 |
| **幂等性** | 相同参数重复调用，副作用不重复 | 重复调用 N 次，验证数据不变 |
| **并发竞争** | 多 goroutine 并发无竞态 | 并发调用，验证最终数据一致 |
| **推送准确** | Push 消息在正确时机触发 | 验证推送内容与业务状态一致 |

**发现的 BUG 类型**：参数校验缺失、幂等实现缺失、并发竞态、panic/crash

#### 维度 2：数据存储一致性测验

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **结构正确性** | 写入的文档字段与设计一致 | 写入后读取，逐字段比对 |
| **读写一致性** | 写入后立即读取一致 | 写后立即读 |
| **跨存储一致性** | MySQL 与 Redis 数据同步 | 分别从两种存储读取对比 |
| **数据隔离** | 不同玩家数据互不串扰 | 玩家 A 写入，玩家 B 读取不到 |
| **默认值** | 新玩家首次使用时默认值正确 | 不预写数据，直接读取 |
| **生命周期** | 创建→写入→重置 各阶段正确 | 分阶段验证 |

**发现的 BUG 类型**：字段类型不匹配、数据覆盖、默认值不合理、缓存与 DB 不一致

#### 维度 3：配置表测验

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **加载正确性** | JSON 能正常加载到内存 | 加载后验证 map 非空 |
| **解析正确性** | 字段类型和值解析正确 | 逐字段类型断言和值对比 |
| **主键唯一性** | 无重复 ID | 遍历检测重复 |
| **表间关联** | 外键引用的记录真实存在 | 交叉查询验证引用完整性 |
| **数值范围** | 数值字段在合理范围内 | 边界校验（上限/下限/零值） |

**发现的 BUG 类型**：主键重复、外键悬挂引用、数值越界、字段类型解析错误

#### 维度 4：业务边界测验

以需求分析报告中识别的问题为**直接输入**，逐一验证：

| 边界类型 | 核心验证 |
|---------|---------|
| **数值边界** | 0、最大值、负数、溢出 |
| **集合边界** | 空集合、满集合、单元素 |
| **时间边界** | 跨天/跨赛季瞬间操作、服务器时间与客户端时间不一致 |
| **身份边界** | 玩家不存在、被封禁、操作目标是自己 |
| **状态机** | 合法流转成功、非法流转被拦截、终态不可变 |
| **时序因果** | 多步骤操作中途失败的回滚、乱序到达的处理 |

**发现的 BUG 类型**：边界条件未处理、状态机流转不完整、时序回滚缺失、组合边界未覆盖

### 第四步：组件架构专项测验

根据被测服务的架构模式，选择对应的专项规范执行测验：

| 服务类型 | 架构模式 | 专项规范 |
|---------|---------|---------|
| mainsvr（role/room） | 有状态 Actor-Component | [specs/有状态微服务组件模块的测验规范.md](specs/有状态微服务组件模块的测验规范.md) |
| connsvr、roomcentersvr、infosvr、mysqlsvr | 无状态 Service-Component | [specs/无状态微服务功能模块的测验规范.md](specs/无状态微服务功能模块的测验规范.md) |

### 第五步：运行测验 + 追踪问题

1. 使用 `go test -v -run "Test{ModuleName}" -timeout 30m ./...` 运行测验（GoOne 测试代码按 Go 模块惯例就近放在对应包内，或统一放在 `lib/internal/itest` 集成测试目录下）
2. 每个失败用例记录到**问题清单**：
   ```
   # | 严重程度 | 问题描述 | 测验维度 | 涉及代码 | 建议修复
   ```
3. 严重程度定义：
   - **致命**：会导致线上事故（数据丢失、重复发奖、panic）
   - **严重**：功能异常但不会直接造成损失（边界未处理、幂等缺失）
   - **一般**：代码质量问题（命名不规范、缺少日志）

### 第六步：输出测试报告

通过 obsidian-cli 生成测试报告到 `{analysis_output_dir}/{需求名称}/测试样例-{日期}.md`。

报告只需包含：

- **测验总览**：范围、通过率
- **问题清单**：所有发现的问题（重点！）
- **测验结论**：通过 / 部分通过 / 未通过

## 测验原则

1. **目标驱动**：核心目标是找出 BUG 和风险，不是"写满测试用例"
2. **边界优先**：优先覆盖需求分析报告中已识别的边界条件（这些是已知的薄弱点）
3. **数据隔离**：使用 `lib/internal/itest` 提供的隔离测试环境，不产生持久化数据
4. **不修改业务代码**：测验只发现和报告问题
5. **问题可追溯**：每个问题标注来源（PRD/需求分析报告章节）

## 测验优先级

| 优先级 | 测验类型 | 原因 |
|--------|---------|------|
| P0（必测） | 协议可靠性 + 异常参数 | 不 crash 是底线 |
| P0（必测） | 数据存储读写一致性 | 数据不丢失是底线 |
| P0（必测） | 需求分析报告中识别的边界条件 | **这些是已知可能出问题的地方** |
| P1（应测） | 幂等性 | 防止重复操作产生副作用 |
| P1（应测） | 配置表关联完整性 | 防止运行时空指针 |
| P1（应测） | 状态机流转 | 防止逻辑死锁 |
| P1（应测） | 组件接口契约 + 生命周期 | 组件化架构的核心约束 |
| P2（建议测） | 并发竞争 | 发现潜在竞态条件 |
| P3（可选） | 压力/性能 | 极端场景 |
