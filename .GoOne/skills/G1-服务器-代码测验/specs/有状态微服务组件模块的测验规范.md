# 有状态微服务组件模块的测验规范

> 适用范围：mainsvr（role/room）等采用 Actor-Component 模式的有状态服务
> 参考实现：`src/mainsvr/role/`（role 子包，承载玩家在线状态与玩法组件）

---

## 一、概述

有状态服务的组件以 Actor-Component 模式运行，组件共享 Actor 生命周期（Init/Load/Online/Offline/Save/Destroy）。测验核心目标：验证组件间的接口契约、生命周期顺序、事件通信、数据隔离和路由注册是否符合设计规范。

> GoOne 的并发模型说明：有状态服务通过 `lib/service/transaction`（TransactionMgr）的**分片串行 key 调度**保证同一玩家（key）的事务串行执行，等效于 Actor mailbox 的语义——同一玩家的请求不会并发进入业务逻辑。测验时应围绕"同一 key 串行、跨 key 隔离"展开。

---

## 二、测验维度

### 维度 1：组件架构与分类

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **核心/扩展划分** | 组件分类与设计文档一致 | 对比设计与实现：Actor 结构体中的核心组件 vs RegisterComponent 注册的扩展组件 |
| **依赖顺序** | 组件初始化/销毁的时序正确 | 验证 Init 顺序遵循依赖关系，Destroy 顺序为逆序 |
| **目录结构** | 核心组件在 base/、扩展组件在 module/ | 检查目录归属是否符合规范 |

**发现的 BUG 类型**：核心组件错放在扩展目录、依赖顺序错误（后初始化组件被先初始化组件调用）、Init 未完成就被外部调用

### 维度 2：组件接口契约

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **接口完整性** | 组件实现了 Name/OnInit/OnDestroy/Load/Save/Online/Offline/DailyReset | 检查组件是否覆写了必需的生命周期方法 |
| **接口类型安全** | 核心组件暴露了类型安全的接口 | 验证 icomponents.go 中的接口定义与实际实现一致 |
| **Actor 能力暴露** | Actor 提供 UID/SysData/RegisterHandler/EventBus/Timer 等方法 | 验证组件是否通过 Actor 接口访问这些能力 |
| **FindComponent** | 扩展组件通过泛型发现其他组件 | 验证是否存在直接持有其他组件实例指针的代码 |

**发现的 BUG 类型**：接口方法签名不一致、组件通过 Actor 结构体直接访问其他组件的私有字段、缺少 BaseComponent 空实现导致不必要的代码

### 维度 3：生命周期与状态

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **Init 顺序** | 基础设施 → 核心组件 → 扩展组件 | 遍历 Init 调用链，验证依赖关系不逆序 |
| **Load 容错** | 无数据时能创建默认数据 | 模拟新玩家（无 DB 数据），验证 Load 不报错 |
| **Save 触发** | 定时 Save + 离线 Save，脏标记正常 | 验证 Save 调用链、脏标记清除时机 |
| **Online** | 上线时推送初始数据给客户端 | 验证 Online 中的推送逻辑 |
| **Offline** | 离线时清理在线状态缓存 | 验证离线后状态被正确清除 |
| **DailyReset** | 跨天重置逻辑正确 | 模拟跨天瞬间，验证每日计数器/任务被重置 |
| **Destroy** | 释放资源、退订事件、取消定时器 | 验证 Destroy 后组件不会收到回调 |

**发现的 BUG 类型**：Offline 未清理缓存导致数据残留、DailyReset 遗漏某些计数器、Save 未触发导致宕机丢数据、Destroy 未退订事件导致内存泄漏

### 维度 4：路由注册

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **cmd 唯一性** | 同一 cmd（uint32 主子命令组合）未被多组件注册 | 遍历所有组件注册的路由表，检测冲突 |
| **注册方式合规** | 组件通过 RegisterHandler 注册，非绕过 | 检查是否直接操作框架 Router |
| **服务级路由预注册** | 路由已在 mainsvr/app.go 中注册 | 验证 app.go 的路由列表包含该 cmd |

**发现的 BUG 类型**：路由冲突（两组件注册相同 cmd）、路由遗漏（app.go 未预注册导致请求无法到达组件）、绕过框架直接操作 Router

### 维度 5：事件通信

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **事件命名规范** | 事件名遵循 `{领域}:{动作}` 格式 | 检查事件常量定义 |
| **订阅/退订配对** | 事件订阅句柄在 OnDestroy 中退订 | 对比 Subscribe 和 Unsubscribe 调用 |
| **禁止循环事件** | 事件处理中不会发布同类型事件 | 检查事件发布→订阅→处理→发布链 |
| **事件 Payload** | 事件携带的数据与订阅者预期一致 | 验证事件结构的字段与消费方的使用一致 |

**发现的 BUG 类型**：订阅后未退订导致 Actor 释放后仍收到事件、A 事件→B 事件→A 事件的循环链、事件 Payload 字段不足导致消费者 panic

### 维度 6：数据持久化与隔离

| 检查点 | 目标 | 方法 |
|--------|------|------|
| **SysID 唯一性** | 每个组件 SysID 唯一且与设计一致 | 验证 protocol.go 中的 SysID 分配 |
| **SysData 隔离** | 组件只读写自己的 SysData | 验证 SetSysData/GetSysData 的 sysID 参数 |
| **关键数据写优先** | 货币/道具类组件先写 DB（MySQL via xorm）再更新内存 | 审查 Save 逻辑中的写入顺序 |
| **定时保存间隔** | Actor 级定时 Save ≤ 60s | 检查 setupSaveTimer 的间隔参数 |
| **事务串行性** | 同一玩家（key）的事务经 TransactionMgr 串行调度 | 构造同 key 并发事务，验证无数据竞争 |

**发现的 BUG 类型**：SysID 冲突（两组件用同 SysID）、跨 SysID 读写（A 组件修改 B 组件的数据）、关键数据未先写 DB（宕机丢失货币）、Save 间隔过长（超过 60 秒）、跨玩家 key 串行调度失效导致竞态

---

## 三、优先检查清单

按以下优先级执行测验（P0 必须在报告前完成）：

- [ ] P0: 核心/扩展组件划分与设计文档一致
- [ ] P0: Init 顺序不违反依赖关系
- [ ] P0: Load 容错（新玩家无数据时不 crash）
- [ ] P0: cmd 路由无冲突
- [ ] P0: SysID 唯一性检查
- [ ] P1: 组件接口签名与 icomponents.go 一致
- [ ] P1: Offline 清理 + Save 触发
- [ ] P1: DailyReset 覆盖完整
- [ ] P1: 事件订阅/退订配对
- [ ] P2: 关键数据写优先策略
- [ ] P2: 定时保存间隔 ≤ 60s
- [ ] P2: 事件循环检测
- [ ] P2: TransactionMgr 同 key 串行调度验证
