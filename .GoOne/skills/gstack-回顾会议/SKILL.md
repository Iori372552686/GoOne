# 每周工程回顾

生成全面的工程回顾，分析提交历史、工作模式和代码质量指标。团队感知：识别运行命令的用户，然后分析每个贡献者，包含每人的表扬和成长机会。

## 参数

- 默认：最近7天
- `24h`：最近24小时
- `14d`：最近14天
- `30d`：最近30天
- `compare`：比较当前窗口与先前相同长度的窗口

## 说明

解析参数以确定时间窗口。默认为7天。所有时间应报告在用户的**本地时区**。

**午夜对齐窗口：** 对于天数单位，在本地午夜计算绝对开始日期。例如，如果今天是2026-03-18且窗口为7天，则开始日期为2026-03-11。对于git日志查询使用`--since="2026-03-11T00:00:00"`。对于小时单位，使用`--since="N hours ago"`。

***

### 步骤1：收集原始数据

首先，获取origin并识别当前用户：

```bash
git fetch origin main --quiet
git config user.name
git config user.email
```

`git config user.name`返回的名称是\*\*"你"\*\* ... 阅读此回顾的人。所有其他作者都是队友。

运行所有这些git命令（它们是独立的）：

```bash
# 所有提交，包含时间戳、主题、哈希、作者、更改的文件
git log origin/main --since="<window>" --format="%H|%aN|%ae|%ai|%s" --shortstat

# 每次提交的测试与总LOC细分，包含作者
git log origin/main --since="<window>" --format="COMMIT:%H|%aN" --numstat

# 提交时间戳，用于会话检测和小时分布
git log origin/main --since="<window>" --format="%at|%aN|%ai|%s" | sort -n

# 最常更改的文件（热点分析）
git log origin/main --since="<window>" --format="" --name-only | grep -v '^$' | sort | uniq -c | sort -rn

# 提交消息中的PR编号
git log origin/main --since="<window>" --format="%s" | grep -oE '[#!][0-9]+' | sort -t'#' -k1 | uniq

# 每位作者的文件热点
git log origin/main --since="<window>" --format="AUTHOR:%aN" --name-only

# 每位作者的提交计数
git shortlog origin/main --since="<window>" -sn --no-merges

# 测试文件计数
find . -name '*.test.*' -o -name '*.spec.*' -o -name '*_test.*' -o -name '*_spec.*' 2>/dev/null | grep -v node_modules | wc -l

# 窗口中更改的测试文件
git log origin/main --since="<window>" --format="" --name-only | grep -E '\.(test|spec)\.' | sort -u | wc -l
```

***

### 步骤2：计算指标

在摘要中计算并呈现这些指标：

- **提交到main：** N
- **贡献者：** N
- **合并的PR：** N
- **总插入：** N
- **总删除：** N
- **净增加LOC：** N
- **测试LOC（插入）：** N
- **测试LOC比率：** N%
- **版本范围：** vX.Y.Z → vX.Y.Z
- **活动天数：** N
- **检测到的会话：** N
- **平均LOC/会话小时：** N

然后立即在下方显示**每位作者的排行榜**：

```
贡献者         提交   +/-          主要领域
你 (garry)              32   +2400/-300   browse/
alice                    12   +800/-150    app/services/
bob                       3   +120/-40     tests/
```

按提交降序排序。当前用户始终排在第一位，标记为"你（姓名）"。

***

### 步骤3：提交时间分布

以本地时间显示小时直方图：

```
小时  提交  ████████████████
 00:    4      ████
 07:    5      █████
 ...
```

识别：

- 高峰时段
- 死区
- 双峰模式（上午/晚上）与连续模式
- 深夜编码集群（晚上10点后）

***

### 步骤4：工作会话检测

使用**45分钟间隔**阈值检测会话。

分类会话：

- **深度会话**（50+分钟）
- **中等会话**（20-50分钟）
- **微会话**（<20分钟，单次提交）

计算：

- 总活跃编码时间
- 平均会话长度
- 每小时活跃时间的LOC

***

### 步骤5：提交类型细分

按约定提交前缀（feat/fix/refactor/test/chore/docs）分类。显示为百分比条：

```
feat:     20  (40%)  ████████████████████
fix:      27  (54%)  ███████████████████████████
refactor:  2  ( 4%)  ██
```

如果修复比率超过50%则标记...表明"快速交付，快速修复"模式，可能表示审查差距。

***

### 步骤6：热点分析

显示前10个最常更改的文件。标记：

- 更改5次以上的文件（流失热点）
- 热点列表中的测试文件与生产文件
- VERSION/CHANGELOG频率

***

### 步骤7：PR大小分布

估计PR大小并分组：

- **小**（<100 LOC）
- **中**（100-500 LOC）
- **大**（500-1500 LOC）
- **XL**（1500+ LOC）

***

### 步骤8：聚焦分数 + 本周最佳交付

**聚焦分数：** 提交触及单个最常更改的顶级目录的百分比。越高=更深的聚焦工作。越低=分散的上下文切换。

**本周最佳交付：** 窗口中LOC最高的单个PR。突出显示PR编号、更改的LOC以及为什么重要。

***

### 步骤9：团队成员分析

对于每个贡献者（包括当前用户），计算：

1. **提交和LOC** ... 总提交、插入、删除、净LOC
2. **聚焦领域** ... 他们最常接触的目录/文件（前3个）
3. **提交类型组合** ... 他们个人的feat/fix/refactor/test细分
4. **会话模式** ... 他们何时编码（高峰时段）、会话计数
5. **测试纪律** ... 他们个人的测试LOC比率
6. **最大交付** ... 他们单个最高影响的提交或PR

**对于当前用户（"你"）：** 最深入的处理。包含所有会话分析、时间模式、聚焦分数。以第一人称表达。

**对于每个队友：** 2-3句话涵盖他们交付的内容和他们的模式。然后：

- **表扬**（1-2个具体事项）：以实际提交为锚点。不是"出色的工作"...确切说出什么好。
- **成长机会**（1个具体事项）：以升级为框架，不是批评。以实际数据为锚点。

**如果是单独仓库：** 跳过团队细分。

**AI协作：** 如果提交有`Co-Authored-By` AI尾部，将"AI辅助提交"作为单独指标跟踪。

***

### 步骤10：周对比趋势（如果窗口>=14d）

按周分组并显示趋势：

- 每周提交（总计和每位作者）
- 每周LOC
- 每周测试比率
- 每周修复比率
- 每周会话计数

***

### 步骤11：连续交付跟踪

从今天开始向后计算至少有1次提交的连续天数：

```bash
# 团队连续天数
git log origin/main --format="%ad" --date=format:"%Y-%m-%d" | sort -u

# 个人连续天数
git log origin/main --author="<user_name>" --format="%ad" --date=format:"%Y-%m-%d" | sort -u
```

显示两者：

- "团队连续交付：47天"
- "你的连续交付：32天"

***

### 步骤12：加载历史记录并比较

检查`memory/`中的先前回顾历史：

如果存在先前回顾，加载最近的一个并计算增量：

```
                    上次        现在         增量
测试比率:         22%    →    41%         ↑19pp
会话:           10     →    14          ↑4
LOC/小时:           200    →    350         ↑75%
修复比率:          54%    →    30%         ↓24pp (改善中)
```

如果没有先前回顾，注意"首次记录回顾，下周再次运行以查看趋势。"

***

### 步骤13：保存回顾历史

将JSON快照保存到`memory/retro-YYYY-MM-DD.json`，包含指标、作者、版本范围、连续天数和可推文摘要。

***

### 步骤14：编写叙述

**Telegram格式**（项目符号、粗体，最终输出中无markdown表格）。

结构：

**可推文摘要**（第一行）：

> 3月1周：47次提交（3位贡献者），3.2k LOC，38%测试，12个PR，高峰：晚上10点 | 连续天数：47d

然后是各节：

- **摘要** ... 关键指标
- **与上次回顾相比的趋势** ... 增量（如果是首次回顾则跳过）
- **时间与会话模式** ... 团队何时编码、会话长度、深度与微
- **交付速度** ... 提交类型、PR大小、修复链检测
- **代码质量信号** ... 测试比率、热点、流失
- **聚焦与亮点** ... 聚焦分数、本周最佳交付
- **你的一周** ... 当前用户的个人深度分析
- **团队细分** ... 每位队友的分析，包含表扬+成长（如果是单独则跳过）
- **团队三大胜利** ... 交付的最高影响事项
- **需要改进的3件事** ... 具体、可操作、以提交为锚点
- **下周的3个习惯** ... 小、实用、现实（采用<5分钟）

***

## 比较模式

当用户说"比较"时：

- 为当前窗口运行回顾
- 为先前相同长度的窗口运行回顾
- 并排呈现指标，用箭头显示改进/退步
- 关于最大变化的简短叙述

***

## 重要规则

- **所有时间使用本地时区。** 绝不设置`TZ`。
- **Telegram格式。** 使用项目符号和粗体。最终输出中避免markdown表格。
- **表扬以提交为锚点。** 绝不没有命名好的地方就说"出色的工作"。
- **成长领域以数据为锚点。** 绝不没有证据就批评。
- **保存历史。** 每次回顾保存到`memory/`以便趋势跟踪。
- **完成状态：**
  - 完成 ... 生成回顾，保存历史
  - 有顾虑完成 ... 生成但缺少数据（例如，没有先前回顾用于比较）
  - 阻塞 ... 不在git仓库中或窗口中没有提交
