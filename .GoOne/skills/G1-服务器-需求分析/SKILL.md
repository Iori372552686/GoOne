# G1-服务器-需求分析

## 概述

本技能以**技术开发者视角**对策划系统需求文档（PRD）进行严格的逻辑审查与边界审查。核心目标是：在需求落地编码之前，找出文档中的逻辑漏洞、规则冲突、状态缺失、边界盲区和需求间的耦合问题。

> **定位边界**：
> - ✅ 审查 PRD 自身的逻辑完备性——规则是否自洽、分支是否覆盖、状态是否闭环
> - ✅ 审查 PRD 与已有需求的耦合——是否存在冲突、重叠、循环依赖
> - ✅ 审查版本迭代中的逻辑一致性——老数据兼容、迁移路径、历史规则
> - ❌ 不审查产品可行性、商业可行性、用户体验优劣（那是策划的事）
> - ❌ 不审查技术实现方案、架构选型、安全性（那是技术设计的事）

## 适用场景

- 策划提交新功能 PRD，开发做需求审查
- 发现已有功能 bug 后回溯 PRD 找根源
- 多个 PRD 同时开发，检查需求间冲突
- 版本迭代时审视需求变更对已有逻辑的冲击
- 排查"需求文档没写但代码该不该做"的灰色地带

---

## 规范遵循（强制）

> 在进行需求分析与逻辑审查时，应先去 `.GoOne/spec/` 目录下自行读取相关规范文档，理解项目的配置表、通讯协议、数据库存储的标准约定，以便在审查需求和评估影响时准确判断耦合关系和兼容性。

## 工作流程

### 第一步：获取项目配置

调用 `G1-项目配置` 技能获取项目配置信息：

> - `vault_path` = Obsidian Vault 路径（用于 obsidian-cli 的 `vault=` 参数）
> - `prd_dir` = 策划需求文档目录（相对 vault 根目录）
> - `analysis_output_dir` = 技术输出目录（相对 vault 根目录）
>
> **输出目录**固定为 `{analysis_output_dir}/{需求名称}/`。

如果 `.GoOne/conf.json` 不存在，`G1-项目配置` 技能会自动引导创建。

---

### 第二步：拉取需求文档及相关文档

1. 根据用户指定的文档名称，通过 obsidian-cli 搜索并读取目标文档：
   ```bash
   obsidian vault="{vault_path}" search query="{文档名称}"
   obsidian vault="{vault_path}" read path="{prd_dir}/{文档名称}"
   ```
2. 扫描文档中 `[[wiki-link]]` 引用，通过 obsidian-cli 递归读取被引用的关联需求文档（最多 2 层）：
   ```bash
   obsidian vault="{vault_path}" read file="{wiki-link名称}"
   ```
3. 通过 obsidian-cli 搜索 vault 下文件名包含相同关键词的其他 `.md` 文件——可能存在同一系统的历史版本需求：
   ```bash
   obsidian vault="{vault_path}" search query="{关键词}"
   ```
4. 收集文档中明确列出的"依赖系统"或"关联模块"清单

---

### 第三步：多维逻辑审查

按以下 **8 个维度** 逐项审查需求文档。每个维度的核心问题是：**"PRD 里有没有说清楚？没说清楚的话，技术上就会出现歧义。"**

---

#### 维度 1：逻辑闭环审查

**核心问题：每个分支是否都有明确的出口？**

- [ ] **触发条件明确性**：功能的触发条件是否完整？是否遗漏了某些触发路径？例如："玩家点击按钮触发"——那 GM 指令触发呢？活动到期自动触发呢？
- [ ] **结果覆盖**：每个 if 分支是否都有对应的 then/else 定义？例如："如果玩家等级≥10，则…"——那等级<10 呢？什么都不发生也是一种结果，但必须明确写出来。
- [ ] **循环终止条件**：涉及循环/重复操作时，终止条件是否明确？无限循环的风险点在哪？
- [ ] **默认行为声明**：当所有显式条件都不满足时，系统的默认行为是什么？PRD 是否明确声明了？
- [ ] **空数据处理**：当依赖数据为空时（无好友、无道具、无匹配对手），行为是否定义？

**输出模板：**
```
### 逻辑闭环问题
| # | 位置 | 问题描述 | 严重程度 | 建议 |
|---|------|---------|---------|------|
| 1 | PRD §3.2 | 等级不足时的行为未定义 | 严重 | 明确拒绝提示文案或降级逻辑 |
```

---

#### 维度 2：规则冲突审查

**核心问题：需求内部的规则是否自洽？需求与已有需求之间是否矛盾？**

- [ ] **内部规则一致性**：同一概念在文档不同位置的定义是否一致？例如：§2 说"每日重置时间为 5:00"，§5 说"每日任务零点刷新"。
- [ ] **优先级冲突**：多条规则同时生效时的优先级是否明确？例如：VIP 免费次数 vs 每日上限 vs 活动赠送次数，谁先生效？
- [ ] **互斥条件**：是否存在"两个条件同时满足但行为不同"的冲突场景？例如：既满足新手保护又满足赛季结算，处理哪个？
- [ ] **数值矛盾**：产出和消耗的数字是否自洽？例如：升级需要 100 经验，单个任务给 30 经验，需要 4 个任务（120 溢出 20），溢出部分怎么处理？
- [ ] **跨需求冲突**：本 PRD 的规则是否与已有 PRD 冲突？例如：好友 PRD 说"删除好友后聊天记录保留"，但本 PRD 说"删除好友清理所有关联数据"。

**审查方法：**
1. 通过 obsidian-cli 搜索涉及相同系统/字段的其他需求文档：
   ```bash
   obsidian vault="{vault_path}" search query="{系统/字段关键词}"
   ```
2. 对比同一概念的定义是否一致
3. 检查是否存在"A 需求要这样，B 需求要那样"的互斥场景

**输出模板：**
```
### 规则冲突问题
| # | 冲突类型 | 冲突描述 | 涉及文档 | 严重程度 | 建议 |
|---|---------|---------|---------|---------|------|
| 1 | 跨需求 | 好友PRD保留记录 vs 本PRD清理数据 | [[好友系统PRD]] §4 | 致命 | 需策划确认统一规则 |
```

---

#### 维度 3：状态机完备性审查

**核心问题：所有状态是否定义完整？所有状态流转是否覆盖？**

- [ ] **状态枚举完整性**：功能涉及的对象（任务/道具/订单/房间）有哪些状态？PRD 是否显式列出了所有状态？
- [ ] **状态流转图**：是否覆盖了所有合法的状态流转路径？（用 Mermaid 画出状态图，逐条核对）
- [ ] **非法流转拦截**：是否定义了哪些流转是禁止的？禁止时应该如何响应？
- [ ] **终态定义**：哪些状态是终态（不可再变更）？终态后收到相关操作请求应如何处理？
- [ ] **并发状态冲突**：同一时刻是否可能同时处于两个状态？例如：正在匹配中又收到组队邀请。
- [ ] **状态与时间的交互**：跨天/跨周/跨赛季时，处于中间状态的对象如何处理？例如：跨天时处于"匹配中"的玩家。

**审查方法：**
- 从 PRD 中提取所有名词（任务、订单、队伍…），逐一审视其状态变化
- 画出状态流转图，检查每条边是否有触发条件、每条非法边是否有处理策略

**输出模板：**
```
### 状态机问题
| # | 对象 | 问题描述 | 严重程度 | 建议 |
|---|------|---------|---------|------|
| 1 | 订单 | "已取消"状态未定义 | 严重 | 补充取消条件、取消后数据保留策略 |
```

---

#### 维度 4：边界条件审查

**核心问题：极限情况下会发生什么？**

- [ ] **数值边界**：
  - 数值为 0 时？（0 次、0 个、0 秒）
  - 数值为 1 时？（单例逻辑的特殊性）
  - 数值为最大值时？（溢出、截断还是拒绝？）
  - 数值为负数时？（扣到负数、属性为负）
- [ ] **集合边界**：
  - 集合为空时？（无好友列表、无可用奖励）
  - 集合满时？（背包 100/100、公会 50/50）
  - 集合只有 1 个元素时？
- [ ] **时间边界**：
  - 同一时刻多个定时事件触发，执行顺序？
  - 跨天/跨周/跨赛季瞬间的操作？
  - 服务器时间与客户端时间不一致？
- [ ] **身份边界**：
  - 玩家不存在时？（已删号玩家的数据被查询）
  - 玩家处于封禁/禁言/游客/防沉迷状态？
  - 目标玩家是自己的情况？给自己的操作？
- [ ] **组合爆炸边界**：多种边界条件同时触发时（如：背包满 + 限时活动结束 + 玩家离线），行为是否合理？

**输出模板：**
```
### 边界条件问题
| # | 边界类型 | 场景 | 严重程度 | 建议 |
|---|---------|------|---------|------|
| 1 | 集合满 | 背包满时活动奖励发放未定义 | 致命 | 明确走邮件补发还是丢弃 |
```

---

#### 维度 5：时序与因果审查

**核心问题：多步骤操作中，每一步失败后会发生什么？**

- [ ] **操作原子性**：多步骤操作（扣钱→发道具→记录日志）是全部成功还是全部失败？如果第 2 步失败，第 1 步是否回滚？
- [ ] **回滚策略**：PRD 是否定义了每个失败场景的回滚行为？回滚到什么状态？
- [ ] **顺序依赖**：A 必须在 B 之前执行吗？如果 B 比 A 先到达（消息乱序），如何处理？
- [ ] **幂等性需求**：哪些操作需要幂等（重复执行不产生副作用）？PRD 是否识别了这些场景？
- [ ] **竞态窗口**：两个操作几乎同时到达时，是否会产生中间状态？例如：同时购买最后一个限量商品。
- [ ] **异步操作链**：如果操作是异步的（等待匹配结果、等待对方确认），超时后如何处理？超时期间的并发操作？

**审查方法：**
- 提取 PRD 中所有多步骤流程，逐步骤问：如果这步失败，前面几步是否回滚？
- 标注所有涉及"发奖励""扣道具""变更状态"的步骤，这些是潜在的失败点

**输出模板：**
```
### 时序因果问题
| # | 操作链路 | 失败点 | 严重程度 | 建议 |
|---|---------|--------|---------|------|
| 1 | 扣钱→发道具 | 发道具失败后钱未定义回滚 | 致命 | 明确回滚策略或使用事务 |
```

---

#### 维度 6：跨需求耦合审查

**核心问题：这个需求与已有需求之间是否存在耦合关系？耦合点是否被双方 PRD 覆盖？**

- [ ] **数据依赖链**：本需求依赖哪些已有系统的数据？这些数据的格式和获取方式在对方 PRD 中有定义吗？
- [ ] **事件触发链**：本需求的操作是否会触发其他系统的行为（如完成任务、解锁成就、影响排行榜）？触发条件在对方 PRD 中是否一致？
- [ ] **共享资源竞争**：本需求和已有需求是否操作同一份数据（如货币、道具、属性）？写入顺序和优先级是否明确？
- [ ] **UI/流程互斥**：本需求的流程是否与现有流程冲突？例如：新需求需要在战斗中加入操作，但现有设计战斗期间禁止外部交互。
- [ ] **耦合强度评估**：标注强耦合（必须联动开发）和弱耦合（可独立开发但有交互），确保强耦合点在 PRD 中都有明确的协议约定。

**审查方法：**
1. 列出本 PRD 涉及的所有数据实体，逐一通过 obsidian-cli 搜索还有哪些 PRD 操作同一实体：
   ```bash
   obsidian vault="{vault_path}" search query="{数据实体名}"
   ```
2. 对于强耦合系统，将两篇 PRD 的相关规则并排对比
3. 检查是否存在"A 改了 B 不知道"的隐性耦合

**输出模板：**
```
### 跨需求耦合问题
| # | 耦合系统 | 耦合类型 | 冲突/缺失描述 | 严重程度 | 建议 |
|---|---------|---------|-------------|---------|------|
| 1 | 任务系统 | 数据写入 | 本需求发奖励但未定义任务进度更新 | 严重 | 补充任务进度事件协议 |
```

---

#### 维度 7：版本迭代兼容审查

**核心问题：新需求上线后，老玩家的存量数据是否兼容？老规则是否平滑过渡？**

- [ ] **存量数据兼容**：已有玩家的数据在新规则下是否可用？是否需要数据迁移脚本？迁移规则是什么？
- [ ] **规则切换时点**：新旧规则切换的精确时间点是什么？切换瞬间处于中间状态的玩家如何处理？
- [ ] **老版本的过渡期**：如果客户端存在旧版本（App 审核延迟、用户未更新），旧客户端访问新服务端时是否兼容？
- [ ] **历史记录处理**：已有的操作记录、排行榜数据、赛季历史在新规则下是否保持一致？
- [ ] **回退策略**：如果新需求上线后需要紧急回滚，数据是否可以恢复？回滚脚本是否考虑？
- [ ] **废弃字段/功能**：如果本需求废弃了某些旧字段或旧功能，旧数据如何处理？直接删除还是保留只读？

**审查方法：**
- 如果需求是修改已有功能，对比旧版 PRD（如有）找出差异点
- 模拟一个"已经玩了 30 天、背包有 200 个道具"的老玩家，逐条过新规则看是否有不合理之处

**输出模板：**
```
### 版本迭代兼容问题
| # | 兼容场景 | 问题描述 | 严重程度 | 建议 |
|---|---------|---------|---------|------|
| 1 | 存量数据 | 旧版道具缺少新规则需要的字段 | 致命 | 定义默认值填充策略或数据迁移方案 |
```

---

#### 维度 8：隐式假设挖掘

**核心问题：PRD 没说但隐含了哪些假设？如果假设不成立会发生什么？**

- [ ] **时序假设**："玩家在线时"——离线时呢？
- [ ] **存在性假设**："从背包中取出道具"——道具不存在呢？被其他操作消耗了呢？
- [ ] **唯一性假设**："获取当前赛季"——同时存在两个赛季（交接期）呢？
- [ ] **不变性假设**："根据玩家等级"——等级在处理过程中变化了呢？
- [ ] **环境假设**："发送邮件通知"——邮件系统宕机了呢？
- [ ] **容量假设**："记录所有对战历史"——上限是多少？无限增长？

**审查方法：**
- 逐句读 PRD，每遇到一个名词就问："如果这个不存在/不可用/已变更，逻辑还成立吗？"
- 标注所有隐含的"总是""一定""必定"等绝对化表述，追问反例

**输出模板：**
```
### 隐式假设问题
| # | 假设 | 反例 | 严重程度 | 建议 |
|---|------|------|---------|------|
| 1 | 赛季总是存在 | 赛季交接期无当前赛季 | 严重 | 明确交接期的默认行为 |
```

---

### 第四步：输出审查报告到知识库

将所有维度的问题汇总，通过 obsidian-cli 输出到知识库指定目录。

**输出命令**：
```bash
obsidian vault="{vault_path}" create name="{analysis_output_dir}/{需求名称}/逻辑审查报告{date}" content="{报告内容}"
```

**报告结构：**

```markdown
# {需求名称} — 逻辑审查报告

> 审查日期：{date}
> 需求文档：[[{PRD路径}]]
> 关联文档：[[{关联PRD1}]] [[{关联PRD2}]]
> 审查状态：待反馈 / 审查中 / 已闭环

| 2 | 赛季交接期行为？ | 严重 | 隐式假设赛季存在 | 建议定义休赛期默认逻辑 |
```

---

### 第五步：反馈与闭环

1. **标记状态**：每个问题标记为 待确认 / 已确认 / 已解决 / 不予处理
2. **发送反馈**：将"待策划确认问题"（附录B）和致命/严重问题发送给策划
3. **回归审查**：策划反馈后更新状态，对修改内容重新走第三步
4. **审查通过**：致命和严重问题全部闭环后，标记"审查通过 ✅"
5. **归档**：已闭环报告通过 obsidian-cli 写入到 `{analysis_output_dir}/{需求名称}/需求分析报告.md`，文件名加日期后缀：
   ```bash
   obsidian vault="{vault_path}" create name="{analysis_output_dir}/{需求名称}/需求分析报告{date}" content="{归档内容}"
   ```

```
PRD提交 → 拉取文档 → 8维审查 → 输出报告
                                    ↓
                               策划反馈
                                    ↓
                           致命/严重闭环?
                            ├── 否 → 回归审查
                            └── 是 → 审查通过 → 归档
```

## 严重程度定义

| 级别 | 定义 | 示例 |
|------|------|------|
| **致命** | 逻辑断裂——按 PRD 现有描述无法完成开发，或必然产生线上事故 | 奖励发放后无任何确认机制，重试必然重复发放 |
| **严重** | 定义缺失——重要分支无说明，开发只能自行脑补，容易出错 | 跨天刷新时刻的中间状态未定义 |
| **一般** | 表述模糊——有说明但不精确，不同开发理解可能不同 | "适当降低概率"没有具体数值 |

## 审查原则

1. **逐句追问**：对 PRD 中的每一句话问"如果条件不满足呢？如果反了呢？"
2. **找反例**：对每个看似显然的规则，构造反例验证
3. **对撞法**：将两条看起来都合理的规则放在一起，检查它们是否冲突
4. **老玩家视角**：始终模拟一个"数据量很大、玩了很多天"的老玩家来审视新规则
5. **不替策划做决策**：只指出问题，不替策划决定答案；建议方案只是引导思路
