# G1-服务器-BUG修复

## 核心目标

> **唯一的、最高的、不可动摇的目标 —— 解决BUG。**

所有工作必须回答一个问题：**"这一步对解决BUG有什么帮助？"**

| 如果答案是... | 那就... |
|--------------|---------|
| 有帮助 | 做 |
| 不确定有没有帮助 | 先做最小成本验证 |
| 没有帮助 | 跳过，不要做 |
| 有干扰（偏离BUG主线） | 坚决不做 |

> 这个技能不是为了做文档溯源、不是为了写测试代码、不是为了输出报告——这些**只是手段**，**解决BUG才是目的**。

---

## 概述

本技能提供一套**以解决BUG为唯一导向**的系统化修复流程：

```
BUG出现 → 最快复现 → 最短路径定位根因 → 最小改动修复 → 验证闭环
```

> **定位边界**：
> - ✅ **只做与解决BUG直接相关的事**
> - ✅ 灵活调用 `G1-服务器-代码测验` 做轻量的代码级测试验证
> - ✅ 灵活调用 `G1-服务器-模拟测试` 做深度的联调级业务链路测试
> - ✅ 根据BUG类型，在两种测试工具之间自由切换，互相补充
> - ✅ 输出报告 → 仅当BUG确认修复后做
> - ❌ 不做无关的需求审查、架构优化、代码重构
> - ❌ 不替代 `G1-服务器-需求分析` 的PRD审查
> - ❌ 不替代 `G1-服务器-技术分析设计` 的方案设计

---

## 适用场景

| 场景 | BUG驱动的心法 |
|------|--------------|
| **线上/测试环境发现BUG** | 最快速度复现，最小改动修复 |
| **模拟测试发现BUG** | 测试给的BUG就是靶子，靶子明确了就不要绕路 |
| **代码测验发现BUG** | 测验报告已指明问题范围，直接深入对应的代码路径 |
| **回归发现的旧BUG** | 之前修复没覆盖完整，追加测试用例补缺口 |
| **跨模块联动异常** | 先确定异常出现在哪个模块的边界上，再下钻 |

---

## 前置条件

1. **BUG必须可复现** — 没有稳定的复现路径，修复无从谈起。
2. **代码可构建** — `./main.sh build`（或 `go build ./...`）必须通过，否则先解决构建问题。
3. **测试环境可用** — `go test` 可运行（代码测验）或 `tools/tester` 可启动（模拟测试）。

---

## BUG适用范围（重要约束）

> 本技能**只处理业务逻辑层面的BUG**，以下类型的问题**不在本技能的处理范围内**。

| 约束 | 说明 | 遇到后怎么办 |
|------|------|------------|
| ❌ **不排查中间件的问题** | etcd/zk（注册中心）、Redis、MySQL、RabbitMQ（bus）等中间件的连接失败、超时、数据异常，不属于业务BUG。这些基础设施默认已就绪，遇到连接错误直接归因为**业务配置错误**或**环境问题**。 | 检查 `server_conf.yaml` 中的地址端口配置是否正确，或确认中间件服务是否已启动（`./main.sh docker up --env dev`） |
| ❌ **不解决技术架构层的BUG** | 服务发现/注册机制、bus 路由、ssrpc 框架、TransactionMgr 调度、runtime.Component 生命周期管理等 `lib/` 框架层的缺陷，不属于业务BUG。 | 记录问题并升级给框架开发团队处理 |
| ✅ **只处理业务性的BUG** | 业务逻辑分支缺失、边界条件遗漏、状态流转错误、数据读写不一致、配置表数据错误、协议校验缺失、跨模块交互遗漏等，属于业务BUG。 | 按本技能的六阶段流程系统化修复 |

> **判断标准**：如果一个问题的根因在 `src/<svc>svr/` 目录之外（如 `lib/`、`module/` 等框架层），或者需要修改中间件配置才能解决，则不属于本技能的修复范围。

## BUG修复的全局决策框架

```
                    ┌─ 能否稳定复现？ ──→  否  ──→ 收集日志，分析代码，构造复现条件
                    │
  拿到BUG ──→  ──→  ┤
                    │
                    └─ 能复现？ ────────→  是  ──→ 能否一眼看出根因？
                                                                      │
                                              ┌────────────────────────┤
                                              │                        │
                                         能一眼看出              不能一眼看出
                                              │                        │
                                              ▼                        ▼
                                        直接修复                 判断BUG类型
                                        → 回归验证                → 选择测试策略
                                                                  → 写测试锁定
                                                                  → 定位根因
                                                                  → 修复
                                                                  → 回归
```

## 工作流程

### 阶段零：30秒快速启动

调用 `G1-项目配置` 技能获取项目配置：

| 配置字段 | 用途 |
|---------|------|
| `vault_path` | Obsidian Vault 路径 |
| `analysis_output_dir` | 技术输出目录 |

知识库路径规则：`{analysis_output_dir}/{模块名称}/...`

---

### 阶段一：缩小包围圈（30分钟内完成）

> **目标**：把搜索范围从全项目缩小到1~2个文件。

#### Step 1.1 根据BUG现象判断模块归属

| BUG现象 | 可能的模块 |
|---------|-----------|
| 道具数量不对、无法使用 | 背包/道具系统 |
| 货币/钻石少了 | 经济/货币系统 |
| 任务无法完成/提交 | 任务/成就系统 |
| 皮肤/装扮显示异常 | 装扮系统 |
| 战斗表现/数值不对 | 战斗/技能系统 |
| 匹配不到人/匹配异常 | 匹配系统 |
| 排行榜数据错误 | 排行榜系统 |
| 社交/好友操作失败 | 社交系统 |

> **决策点**：如果BUG现象直接指向某个具体模块，跳过Step 1.2，直接进入源码分析。

#### Step 1.2 按需快速扫读文档

仅当以下情况才读文档：
- **不理解BUG涉及的业务逻辑** — 读需求分析报告和技术方案
- **怀疑是历史遗留问题** — 读历史BUG修复报告

```bash
obsidian vault="{vault_path}" read path="{analysis_output_dir}/{模块名称}/需求分析报告.md"
obsidian vault="{vault_path}" read path="{analysis_output_dir}/{模块名称}/BUG修复报告.md"
```

**扫读要点**：
- 需求分析报告 → 只看"逻辑闭环"和"边界条件"章节
- 历史BUG报告 → 只看"BUG归因"部分，对比是否同类

> **决策点**：读文档后如果能定位到问题方向，立即进入源码分析。

#### Step 1.3 代码搜索快速锁定

用 grep / 代码搜索工具快速定位嫌疑符号、调用链：

```bash
# 搜索符号定义/引用
grep -rn "{模块关键词}" src/ lib/ module/ --include="*.go"
# 查找某函数的调用方
grep -rn "{嫌疑函数}(" src/ --include="*.go"
```

> **决策点**：如果直接找到BUG位置，跳转到阶段四修复。

---

### 阶段一·五：选择测试策略（因地制宜选工具）

> **为什么要做**：不同BUG适合用不同的测试工具。选对工具，事半功倍。**测试本身不是目的，快速定位和验证BUG才是。**
>
> **当前 tester 默认使用回归模式（regression）**，即 all-in-one 单元/集成测试：跑完整用例集、输出 PASS/FAIL。只有在需要并发饱和验证时才切到 stress 压测模式。

#### 三条测试路径速览

```
                    ┌─ 轻量路径：代码测验（go test）
                    │   适用：配置表问题、存储读写问题、
 根据BUG类型选择 ──→┤        简单协议校验、组件接口契约
                    │   特点：无外部依赖、秒级运行、lib/internal/itest mock
                    │   调用技能：G1-服务器-代码测验
                    │
                    ├─ 默认路径：tester 回归模式（regression）
                    │   适用：复杂业务链路、多模块联动、状态机流转
                    │   特点：all-in-one、跑完整用例集、输出 PASS/FAIL
                    │   调用：go run ./tools/tester/cmd/tester -config ./tools/tester/tester.toml
                    │
                    └─ 深度并发路径：tester 压测模式（stress）
                        适用：并发竞态、数据串扰、资源泄漏、饱和测试
                        特点：多玩家循环跑、生成压测报告
                        调用：go run ./tools/tester/cmd/stress -config ./tools/tester/stress.toml
```

#### 详细选择矩阵

| BUG类型 | 推荐工具 | 原因 | 具体用法 |
|---------|---------|------|---------|
| **配置表数据错误**（ID不存在、数值越界、关联断裂） | **代码测验** | 配置表测验是代码测验的专长维度，go test + lib/internal/itest mock 即可完成，无需启动外部服务 | 调用代码测验的"配置表测验"维度，检查配置加载、主键唯一性、表间关联 |
| **数据存储读写不一致**（写进去读不出来、字段对不上） | **代码测验** | 数据存储一致性测验专门覆盖读写一致性、跨存储一致性、数据隔离，同样无需外部服务 | 调用代码测验的"数据存储一致性测验"维度 |
| **简单协议校验缺失**（参数没校验、错误码不对） | **代码测验** | 协议的异常参数、幂等性、边界测试都可以通过 go test 快速验证 | 调用代码测验的"通讯协议接口测验"维度 |
| **组件接口/生命周期问题**（有状态/无状态组件契约） | **代码测验** | 代码测验有专门的组件架构专项规范，可深挖组件化架构的接口和生命周期问题 | 调用代码测验的"组件架构专项测验"维度 |
| **复杂业务链路异常**（多步操作、状态机流转、跨系统联动） | **tester regression（默认）** | 回归模式模拟真实客户端行为，能完整覆盖业务链路中的每一步验证 | 启用对应模块后运行回归测试，查看哪条用例 FAIL |
| **多模块联动BUG**（A模块改了B模块没同步） | **tester regression（默认）** | 回归组件可以聚合多个模块在一个测试实体中形成闭合链路 | 在 `tester.toml` 中启用多个模块，运行回归测试 |
| **并发竞态/数据串扰**（多人同时操作、排行榜、全服邮件） | **tester stress** | stress 支持多玩家饱和测试，能有效排查并发竞态和资源泄漏 | 配置 `[player].players` 和 `[stress].duration` 后运行 stress |
| **回归验证**（修复后是否引入新问题） | **代码测验 + tester regression** | 代码测验保证基础功能不受影响（轻量高频），回归测试保证业务链路完整（深度低频） | 先跑代码测验全量，再跑 tester regression |

#### 何时切换工具

BUG修复过程中，**工具不是锁定不变的**，可以根据实际情况灵活切换：

```
用代码测验发现配置表有问题
  → 修完配置表后，发现配置表改动影响了业务逻辑
  → 切换到 tester regression，跑一次完整的业务链路验证
```

```
用 tester regression 发现某个协议的参数校验缺失
  → 修完参数校验后，用代码测验快速验证各种边界参数
  → 确认边界都处理后，再用 tester regression 跑一次完整链路回归
```

```
用 tester regression 验证通过，但线上仍出现偶发数据串扰
  → 切换到 tester stress，配置多玩家并发场景做饱和验证
```

> **核心理念**：什么工具能最快解决当前问题，就用什么。同一个BUG的修复过程中，可以在代码测验 / tester regression / tester stress 之间来回切换。

### 阶段二：源码钻取定位根因（2小时内完成）

> **目标**：找到确切的代码行和逻辑错误。

#### Step 2.1 BUG路径追溯法

从BUG的表现现象出发，沿着**数据流**逆向追溯：

```
BUG现象（外部表现）
    ↓ 这是什么数据/状态出了问题？
数据/状态异常
    ↓ 这个数据/状态是谁写入的？
写入方
    ↓ 写入时用的什么逻辑？
写入逻辑
    ↓ 逻辑的输入是什么？输入是否正确？
输入数据/上游调用
    ↓ 输入数据/调用的源头是哪里？
源头 → 根因
```

**示例**：玩家装扮没有生效
```
玩家外观没变化 → 装扮数据没同步到场景
→ S2C_PlayerAppearanceSync 没有在切换装扮时发送
→ handler 处理 ChangeCostume 时遗漏了 sync 调用
→ 根因：ChangeCostume handler 缺少 syncAppearance() 调用
```

#### Step 2.2 八维根因检查表

| # | 维度 | 自检问题 | 适合的验证工具 |
|---|------|---------|--------------|
| 1 | **逻辑分支缺失** | if-else是否覆盖所有分支？switch是否有default？ | 代码测验（协议异常参数测试） |
| 2 | **边界条件遗漏** | 空数组、0值、nil、最大值、重复操作是否处理？ | 代码测验（业务边界测验） |
| 3 | **状态流转错误** | 状态机是否允许当前状态执行此操作？ | tester regression（完整操作序列验证） |
| 4 | **数据一致性** | 缓存和DB是否同步？并发写是否有锁？ | 代码测验（存储一致性）+ tester stress（并发场景） |
| 5 | **时序问题** | 多步操作中某一步失败，后续是否继续执行？ | tester regression / stress（模拟中断/超时场景） |
| 6 | **配置表读取** | 配置表ID是否存在？字段是否越界？ | 代码测验（配置表测验） |
| 7 | **协议处理** | 请求字段是否做了合法性校验？ | 代码测验（协议鲁棒性测试） |
| 8 | **跨模块交互** | 修改A模块数据后，是否通知了依赖A的B模块？ | tester regression（多模块聚合测试） |

> 每一维度的检查项后面都标注了"适合的验证工具"。在定位到根因后，可以直接参考该列，选用对应的工具进行验证。

#### Step 2.3 输出根因结论

```
根因：{一句话概述}
涉及文件：{文件路径:行号}
错误类型：{逻辑分支缺失/边界遗漏/状态流转错误/...}
修复方向：{如何修正}
推荐验证方式：{代码测验 / tester regression / tester stress / 两者结合}
```

### 阶段三：写测试复现并锁定BUG

> **目标**：用测试稳定复现BUG，确认根因正确。

#### Step 3.1 判断是否需要写测试

| 场景 | 是否写测试 | 原因 |
|------|-----------|------|
| BUG可稳定手动复现，且修复改动极小 | 可以跳过 | 手动验证效率更高 |
| BUG涉及复杂链路或多模块联动 | 必须写 | 需要自动化反复验证 |
| BUG修复后需要长期回归 | 必须写 | 防止再次引入 |
| BUG的根因是通过代码推理得到的 | 必须写 | 需要实际验证推理正确 |

> **写不写测试，唯一标准是"能不能更快解决BUG"**。

#### Step 3.2 路径A：轻量验证 — 调用「代码测验」

> **适用场景**：配置表问题、数据存储问题、简单协议校验、组件接口契约

调用 `G1-服务器-代码测验` 技能，在已有测验中追加对应的测试用例，或直接运行现有测验来验证。

**典型用法**：

```bash
# 直接运行代码测验，检查对应模块
go test -v -run "Test{模块名}" -timeout 30m ./...
```

**示例场景**：
- 配置表ID不存在 → 运行配置表测验，检查主键唯一性和引用完整性
- 参数校验缺失 → 运行协议测验，检查异常参数（零值、负值、超大值）是否触发错误码
- 数据存储不一致 → 运行存储测验，检查写入后读取是否一致

> **为什么选代码测验**：无外部依赖，lib/internal/itest mock 隔离数据，秒级运行，可以快速验证代码层的问题。在BUG修复的初期阶段，优先用最轻量的方式验证。

#### Step 3.3 路径B：默认路径 — 调用「tester regression」

> **适用场景**：复杂业务链路、多模块联动、状态机流转、真实玩家行为

`tools/tester` 的默认模式是 **regression（all-in-one 回归/单元测试）**：单进程拉起 gate + 各服务 + 模拟客户端，跑完整用例集并输出 PASS/FAIL。只有在需要并发饱和验证时才切到 stress 模式。

**启用指定模块**：

回归测试不再使用旧的 `-modules` 命令行参数，而是在 `tools/tester/tester.toml` 中通过 `[modules.<name>]` 开关控制：

```toml
[modules.backpack]
enabled = true
order = 1

[modules.shop]
enabled = true
order = 2
```

**最小复现用例模板**：

```go
func (c *XxxComponent) Test_BUGName_Reproduce(ctx context.Context) error {
    // Step 1: 准备数据（GM注入必要数据：直接构造对应 GM proto 请求发送）
    c.prepareData(ctx)

    // Step 2: 复现BUG的操作序列（RequestProto: ctx, cmd, req, rsp, timeout）
    resp := &pb.SomeRsp{}
    if err := c.requester.RequestProto(ctx, uint32(pb.CMD_MAIN_XXX_REQ), &pb.SomeReq{...}, resp, 10*time.Second); err != nil {
        return fmt.Errorf("request failed: %w", err)
    }

    // Step 3: 验证BUG是否出现
    if resp.SomeField != expectedValue {
        return fmt.Errorf("BUG复现成功: 期望 %v, 实际 %v", expectedValue, resp.SomeField)
    }

    return nil
}
```

**构建并运行**：

```bash
# 构建（可选，go run 会自动编译）
./build.sh tester

# 启动回归测试（须先启动被测服务器：connsvr/mainsvr 等）
go run ./tools/tester/cmd/tester -config ./tools/tester/tester.toml
```

- 配置文件：`tools/tester/tester.toml`（`[run].mode` 须为 `regression`）
- 外部依赖：被测服务器须已启动，且 ZK/etcd（注册中心）、Redis、MySQL、RabbitMQ（bus）可用
- 启动后自动发起测试，完成后以退出码 0/1 表示结果

**何时切到 stress**：

```toml
[run]
mode = "stress"
```

```bash
go run ./tools/tester/cmd/stress -config ./tools/tester/stress.toml
```

> **为什么选 tester regression**：默认 all-in-one，能覆盖完整的业务链路和模块间交互，且输出明确的 PASS/FAIL。复杂链路或多模块联动BUG的首选验证方式。

#### Step 3.4 路径切换决策

```
用代码测验后发现：
  测试通过（BUG没有复现）→ BUG可能不在代码层面，切换到 tester regression 做链路验证
  测试失败（BUG稳定复现）→ 根因确认，进入阶段四修复

用 tester regression 后发现：
  测试通过（BUG没有复现）→ 根因假设错了，回到阶段二重新分析
  测试失败（BUG稳定复现）→ 根因确认，进入阶段四修复

用 tester stress 后发现：
  测试通过（BUG没有复现）→ 并发假设不成立，回到阶段二重新分析
  测试失败（BUG稳定复现）→ 根因确认，进入阶段四修复

中途发现BUG类型变了：
  例如：准备用 tester regression，但发现实际上是配置表问题 → 切换到代码测验，更快验证
  例如：用代码测验修好了参数校验，但发现还有链路问题 → 切换到 tester regression，跑完整链路
  例如：回归通过但线上偶发串扰 → 切换到 tester stress，做并发饱和验证
```

> **切换机制**：测试不是一次性选择。在根因定位和修复过程中，可以根据进展随时切换测试工具。目标始终是"最快解决BUG"。

### 阶段四：修复→验证→闭环

#### Step 4.1 最小修改修复

```
修复铁律：
- 只改有问题的代码行，不改相邻的、无关的代码
- 不改缩进、不改命名、不改注释、不重构
- 如果修复需要改动超过5处，说明根因可能没找对
```

#### Step 4.2 回归验证 — 双重防线

修复完成后，根据BUG类型和修复范围选择回归策略：

| 修复范围 | 推荐回归策略 | 具体操作 |
|---------|-------------|---------|
| **仅改了配置表**（无代码改动） | 代码测验回归 | 运行配置表测验，确认加载和引用完整性正常 |
| **改了单模块内的代码逻辑** | 代码测验回归 | 运行该模块的协议测验和业务边界测验 |
| **改了跨模块交互逻辑** | 代码测验 + tester regression | 先用代码测验确认各模块自身功能正常，再用 tester regression 跑完整链路 |
| **涉及并发/多人场景** | tester stress 回归 | 配置 `[player].players=100` 跑饱和测试，排查数据串扰 |

**回归命令**：

```bash
# 代码测验回归（轻量、快速）
go test -v -run "Test{模块名}" -timeout 30m ./...

# tester regression（默认深度验证）
./build.sh tester
cd bin
go run ./tools/tester/cmd/tester -config ./tools/tester/tester.toml

# tester stress（并发饱和验证）
./build.sh stress
cd bin
.\bin\go run ./tools/tester/cmd/stress -config ./tools/tester/stress.toml
```

#### Step 4.3 追加回归用例

在原BUG复现的基础上，追加1~3个变体用例：

```
原BUG：购买道具时，数量为0时没有报错，直接扣了钱
追加用例1：数量为负数时
追加用例2：数量超过背包上限时
追加用例3：数量为极大值（int32最大值）时
```

追加的用例写入到对应的测试代码中：
- 代码测验 → `test/` 目录下的测试文件
- tester regression/stress → `tools/tester/app/component/<name>/` 下的组件文件

#### Step 4.4 收敛判断

```
检查清单：
□ 根因分析是否确认？                 → 能一句话说清楚"这段代码为什么错了"
□ 修复是否最小化？                   → 只改了必须改的代码行
□ 代码测验回归是否通过？             → go test 返回 PASS（如适用）
□ tester regression 是否通过？       → tester 退出码 0（如适用）
□ tester stress 是否通过？           → stress 退出码 0（如适用）
□ 追加的变体用例是否全部通过？         → 同类场景都已覆盖

以上全部 ✅ → BUG闭环
任意一项 ❌ → 回到对应的步骤
```

## 原则（BUG修复的10条军规）

### 1. BUG至上的目标法则
**时刻问自己"这一步对解决BUG有什么帮助？"** 有帮助就做，没帮助就跳过，有干扰就坚决不做。

### 2. 最小修改法则
**只改有问题的代码，不做任何无关重构。** 如果修复需要改5处以上，很可能是根因没找对。

### 3. 先复现再修复法则
**修复前必须能稳定复现BUG。** 不能稳定复现的BUG，修复了也无法验证是否修好。

### 4. 工具匹配法则
**用对的工具测对的BUG。**
- 配置表/存储/协议/组件契约问题 → 优先代码测验（轻量快速）
- 复杂业务链路/多模块联动/状态流转 → **默认 tester regression**（all-in-one 回归测试）
- 并发竞态/数据串扰/饱和测试 → tester stress（深度全面）

两种工具可以灵活切换，**不要用锤子去拧螺丝，也不要用螺丝刀去砸钉子**。

### 5. 最小测试法则
**测试代码以"够用"为原则。** 能用一个用例复现，就不写十个。代码测验能验证的，就不启动 tester regression。regression 能验证的，就不启动 stress。等根因确认后再根据回归需要决定是否扩充用例。

### 6. 聚合测试法则
**如果BUG涉及N个模块联动，测试代码必须在一个测试实体中形成闭合链路。** 代码测验聚合在同一个 Test 函数中，tester regression/stress 聚合在同一个 module 组件中。

### 7. 双重回归法则
**修改跨模块逻辑后，必须通过两道回归防线：** 代码测验保证各模块自身功能正常，tester regression 保证业务链路完整。单模块内的改动可以只跑代码测验。

### 8. 打穿同类场景法则
**修完一个BUG，补上1~3个"亲戚用例"。** 边界值、负向值、零值——补上这些变体用例，断了同类问题的后路。

### 9. 精简复盘法则
**复盘是为了提取"下次怎么防得住"。** 把答案提炼成一条可执行的检查项，加到下次的checklist里。

### 10. 时间盒法则
**每个阶段设置硬性时限，超时就升级决策。**

| 阶段 | 时限 | 超时后 |
|------|------|--------|
| 阶段一（缩小包围圈） | 30分钟 | 整理已有线索，决定继续深入或请求帮助 |
| 阶段二（源码定位根因） | 2小时 | 列出所有假设，请求代码评审 |
| 阶段三（写测试复现） | 与阶段二并行 | 如果阶段二已确认根因，测试不是必需的 |
| 阶段四（修复→验证） | 无硬性限制 | 但每次迭代必须比上一次更快 |
| 阶段五（输出报告） | 修复完成后30分钟内 | 确保BUG还在脑子里的时候写完 |
