# 通讯协议规范文档

> **`g1_common` 子模块是协议定义中心** — 共享消息、枚举、CMD 常量、service proto 源文件均位于 `common/game_proto/`，生成代码在 `api/gen/` 与 `common/protocol/`。服务间 RPC 通过 **ssrpc IDL**（`api/proto/goone/options/v1/options.proto` 扩展）声明并生成。

## 1. 概述

GoOne 的消息分三类：
- **C2S / S2C**（客户端 ↔ 服务端）：客户端经 `connsvr` 接入，消息体为 protobuf，包头是固定 28 字节的 `CSPacketHeader`。
- **S2S**（服务端 ↔ 服务端）：经 bus（默认 RabbitMQ）转发，包头是 `SSPacketHeader`（含 trace 字段），由 ssrpc 生成 wrapper。

消息分发通过 **cmd**（命令字）路由：cmd 高 16 位编码 `ServerType`，由 `lib/service/router` 按 `ServerRouteRules` 选定目标服务实例。

```
│   ├── client.proto             # 客户端消息（LoginReq/Rsp 等）

```

### 2.2 目录选择

| 目录 | 放什么 |
|------|--------|
| `service/` | 服务的 proto service 定义 + ssrpc option（IDL 入口） |
| `core/` | 跨服务共享的消息结构、枚举、CMD、错误码 |
| `config/` | 配置表结构（由 cfgtool 生成，见 [01-游戏配置规范文档.md](./01-游戏配置规范文档.md)） |
| `storage/` | 面向 dbsvr 的统一 KV 抽象（DBUidGet/Set 等） |

`api/proto/goone/` 下是 GoOne 仓库自有的 proto：`options/v1/options.proto`（ssrpc IDL 扩展）与 `cmd/v1/cmd.proto`（由 `tools/cmd/gencmdproto` 从 `core/cmd.proto` 镜像生成）。

## 3. ssrpc IDL 扩展

### 3.1 扩展号

`api/proto/goone/options/v1/options.proto` 定义两个扩展：

```proto
extend google.protobuf.MethodOptions  { SsRpc     ssrpc         = 61001; }
extend google.protobuf.ServiceOptions { SsRpcService ssrpc_service = 61002; }
```

### 3.2 SsRpc 字段

| 字段 | 说明 |
|------|------|
| `cmd` | 直接指定 cmd 数值（优先级最高） |
| `cmd_name` | 引用 `g1_protocol.CMD` 常量名（如 `"CMD_MAIN_LOGIN_REQ"`），cmd 解析优先级：`cmd` > `cmd_enum` > `cmd_name` |
| `cmd_resp` | 响应 cmd（缺省 `cmd+1`） |
| `one_way` | 单向消息（无响应） |
| `uid_lock` | 按 UID 串行（加锁） |
| `auth` / `sign` | 是否需要鉴权 / 签名 |
| `ws` | 是否经 WS 暴露（connsvr 登录前置） |
| `grpc` / `grpc_service` | gRPC 暴露 |
| `http_path` / `http_method` | HTTP 暴露（web_svr） |
| `timeout_ms` | 超时（service 级可设默认） |
| `trace_tags` / `comment` | trace 标签 / 注释 |

### 3.3 真实示例

C2S（WS 暴露，cmd_name 绑定）：
```proto
rpc Login(g1.protocol.LoginReq) returns (g1.protocol.LoginRsp) {
  option (goone.options.v1.ssrpc) = {
    cmd_name: "CMD_MAIN_LOGIN_REQ"
    ws: true
    comment: "mainsvr login"
  };
}
```

S2S one_way（直接写死 cmd 数值）：
```proto
rpc Tick(g1.protocol.InnerTickReq) returns (google.protobuf.Empty) {
  option (goone.options.v1.ssrpc) = {
    cmd: 0x0B1008
    one_way: true
    comment: "roomcentersvr tick (one-way)"
  };
}
```

HTTP 端点（web_svr）：
```proto
rpc MsgSecCheck(MsgSecCheckReq) returns (MsgSecCheckRsp) {
  option (goone.options.v1.ssrpc) = {
    http_path: "/v1/web/msg-sec-check"
    http_method: "POST"
    sign: true
    comment: "msg security check"
  };
}
```

## 4. CMD 命名空间（双轨制）

GoOne 的 cmd 常量有**两个来源**，命名空间不同：

| 来源 | 位置 | 命名 | 角色 |
|------|------|------|------|
| `common/protocol.CMD` | `core/cmd.proto` 生成 | 带 `CMD_` 前缀（`CMD_MAIN_LOGIN_REQ`） | **source of truth**，ssrpc 的 `cmd_name` 引用它 |
| `api/proto/goone/cmd/v1/cmd.proto` | `tools/cmd/gencmdproto` 镜像生成 | 不带 `CMD_` 前缀（`MAIN_LOGIN_REQ`） | GoOne 内部生成代码用 |

### 4.1 cmd 编码规则（`module/misc/func.go`）

cmd 为 32 位整数，位布局：`[高8位保留][8位 ServerType][4位 MsgType][12位 序号]`

- `ServerTypeInCmd(cmd) = cmd >> 16 & 0xff`（高 16 位取低 8 位 = ServerType）
- `MsgTypeInCmd(cmd) = cmd >> 12 & 0xf`（bit12-15）
- `IsClientCmd`：MsgType == 0 或 3（客户端消息）
- `IsInnerCmd`：!IsClientCmd（服务间内部消息，MsgType 通常 = 1）
- `IsGmCmd`：MsgType == 0xa（GM 命令）

### 4.2 ServerType 号段分配（`module/misc/constant.go`）

cmd 高位编码 ServerType，每个服务的命令字落在自己的号段：

| ServerType | 值 | 号段前缀 | 代表 CMD |
|---|---|---|---|
| ConnSvr | 1 | `0x11000+` | `CONN_KICK_OUT_REQ=0x11000`、`CONN_BROADCAST_REQ=0x11002` |
| MainSvr | 2 | `0x20000+` | `MAIN_LOGIN_REQ=0x20000`、`MAIN_HEARTBEAT=0x20004`、`MAIN_GAME_DO_BET=0x20202`、`MAIN_GM_GET_ROLE=0x2A000` |
| InfoSvr | 3 | `0x30000+` / `0x31000+`(inner) | `INFO_GET_BRIEF_INFO_REQ=0x30000`、`INFO_INNER_SET_BRIEF_INFO_REQ=0x31000` |
| MysqlSvr | 4 | `0x41000+` | `MYSQL_INNER_UPDATE_ROLE_INFO_REQ=0x41000`、`MYSQL_INNER_QUERY_ROOM_INFO=0x41008` |
| MailSvr | 6 | `0x60000+` / `0x61000+` | `MAIL_GET_MAIL_LIST=0x60000` |
| ChatSvr | 7 | `0x70000+` | `CHAT_CHAT_REQ=0x70000` |
| FriendSvr | 8 | `0x80000+` / `0x81000+` | `FRIEND_ADD_FRIEND=0x80002` |
| RoomCenterSvr | 11 | `0xB1000+` | `ROOM_CENTER_INNER_TICK_REQ=0xB1008`、`ROOM_CENTER_INNER_ROOM_LIST=0xB1002` |
| WebSvr | 12 | - | web_svr 多走 HTTP/gRPC，不一定配 cmd |
| TexasGameSvr | 0x50 | `0x501000+` | `TEXAS_INNER_CREATEROOM_REQ=0x501000`、`TEXAS_INNER_TICK_REQ=0x50102E` |

S2C 下行（ServerType=0）：`SC_KICK_OUT=0x3001`、`SC_SYNC_USER_DATA=0x3002`、`SC_CHAT=0x3003` 等。

### 4.3 新增 cmd 流程

1. 在 `common/game_proto/core/cmd.proto` 的 `CMD` 枚举里新增常量（`CMD_<SVR>_<ACTION>_<REQ|RSP>`，数值按 ServerType 号段 + 序号，REQ/RSP 用连续偶/奇）
2. 在对应 `service/*.proto` 的 rpc method 上配 ssrpc option（`cmd_name` 引用新常量，或 `cmd` 直接写数值）
3. 运行 `go run ./tools/cmd/genproto`（主仓）+ 必要时 `./main.sh proto game`（子模块）
4. 校验：`./main.sh check-genproto`（`--full` 同时校验 common/protocol）
5. 重新生成 cmd 镜像：`go run ./tools/cmd/gencmdproto`（更新 `api/proto/goone/cmd/v1/cmd.proto`）

## 5. 消息命名

### 5.1 风格

- proto message：PascalCase，如 `LoginReq`、`LoginRsp`、`RoleInfo`、`MysqlTexasRoomInfo`
- cmd 常量：`<SVR>_<ACTION>_<REQ|RSP>`（如 `MAIN_LOGIN_REQ`/`MAIN_LOGIN_RSP`）
- 错误码：`ERR_<MODULE>_<NAME>`（见 `core/error_code.proto`）

### 5.2 字段编号

| 范围 | 用途 |
|------|------|
| =1~20 | 核心业务字段 |
| =21~98 | 业务参数 |
| =99 | 错误码（约定俗成） |
| =100+ | 扩展数据 |

## 6. 传输层映射

不同传输的 handler 挂载方式（见 README §3.1）：

| 传输 | Wrap 函数 | 挂载点 | Proto option |
|---|---|---|---|
| SSPacket（bus 主通路） | `WrapUnary` | `TransactionMgr` | `cmd`/`cmd_name` |
| HTTP | `WrapHTTPGin` | `gin.IRoutes` | `http_path`/`http_method` |
| WS | `WrapWS` | `ssrpc.Dispatcher` | `ws: true` |
| gRPC | `WrapGRPCUnary` / `WrapGRPCServerStreamTyped` | `grpc.Server` | `grpc: true` |

边界：HTTP-only / gRPC-unary method 可不配 cmd；ws 当前仍要求 cmd 绑定；gRPC server-streaming 必须 grpc-only；client/bidi-streaming 尚未支持。

## 7. 生成代码边界

**禁止手改**（`AGENTS.md` "Generated Code Boundaries"）：
- `api/gen/**`（`.goone_ssrpc.gen.go` + `.pb.go`）
- `common/protocol/*.pb.go`

每个 service 的生成产物导出：`<Svc>ServiceSS` 接口、`New<Svc>SServer(impl, opts)`、`<Svc>Bindings(srv)`、`Register<Svc>ToRegistry(r, srv)`。后者是**推荐注册方式**，由 `ssrpc.NewRegistryComponent` 消费。

> ⚠️ CI 静态门禁禁止生产代码调用 `RegisterXxxToDispatcher` / `RegisterXxxToTransactionMgr` / `TransMgr.RegisterCmd`（遗留兼容路径，仅生成代码内部可用）。

## 8. 错误码定义规范

1. 在 `common/game_proto/core/error_code.proto` 中定义错误码枚举，格式 `ERR_{MODULE}_{ERROR_NAME} = {CODE};`，附中文描述注释
2. 错误码应具有唯一性，模块内避免重复
3. 每个独立模块的错误码定义前后应有明显注释分隔（如 `// --- Main 模块错误码 ---`）
4. 代码中返回错误统一用 `lib/api/gerr`（或 ssrpc 的 `ssrpc.E`/`Wrap`），禁止裸 `errors.New` 穿越 RPC；禁止 `rsp.Ret.Code = ERR_X` 后 `return rsp, nil`（中间件会误统计成功）

---

## 9. 约束

- 不可删除已发布 proto 字段，仅标记废弃；不可修改已有字段编号，仅可新增
- 推送/通知消息名应包含业务模块名
- 代码中用枚举常量而非硬编码数字
- 生成代码的注释保持中文（便于理解字段与错误码含义）
- `SSPacketHeader` v2 起含 trace 字段，是破坏性变更，需整组发版，不支持滚动混布
